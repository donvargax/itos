# itos 2.3.0

itos for Claude Code. This repository is now a Claude Code plugin marketplace, and its one plugin,
`itos`, is released from this repository with a version of its own (since T-074 it is
raised only when the plugin changes, not with each itos release). In a repository itos manages, it writes each
itos ID's title beside it in Claude's replies, gives Claude a short skill on working with itos, and
turns away an agent's `git commit` and `git push` in favor of `itos commit` and `itos push`. Two
new commands carry it: `itos hook pre-tool-use`, the guard the plugin wires before every Bash
command, and `itos work list`, every item of the work registry with its title, which the titles
read. A repository that pins an itos older than the guard gets no answer from the launcher rather
than a blocked Bash command.

v2.3.0 is additive and asks nothing of a consumer. No key is added, removed or renamed and no
default changes, so a config v2.2.0 accepts, v2.3.0 accepts and reads the same, and `hooks.bin`
keeps its default, `tools/bin/itos`, until v3. A project on the install script moves to v2.3.0
with one `build` commit, the script's version and hashes (Upgrading, step 1); a project that pins
a release moves with the pin's two lines (step 2). The plugin is for whoever wants it, in their
own Claude Code (step 6), and needs an itos of 2.3.0 or later on the `PATH`. Every commit of the
release says `Upgrading: none` (step 5).

## What is new

- **`itos hook pre-tool-use`, the guard** (slice 42, `ID-GUARD-01` to `ID-GUARD-10`). Claude
  Code's `PreToolUse` hook, which the plugin runs before each Bash command. It reads Claude Code's
  JSON on stdin (`tool_name`, `tool_input.command`, `cwd`) and, in a repository itos manages (an
  `itos.yaml` in the input's folder or at its repository's top, or a stealth config; with no `cwd`,
  the folder itos runs in), denies a Bash command that runs `git commit` or `git push`: exit 0 and
  Claude Code's deny on stdout, its reason naming the itos command to use, which Claude Code shows
  the agent:

  ```text
  git commit is itos commit in this repository: run itos commit --task <id>, or itos commit --scenarios <ids>, with the same arguments, so the commit carries the footers it needs (itos commit --help).
  git push is itos push in this repository: run itos push, with no arguments; it pulls the upstream with a rebase, then pushes HEAD to it, never forced (itos push --help).
  ```

  Everything else gets no answer (exit 0, nothing on stdout), never an allow, so your own
  permission rules still decide as if no hook ran. The command is read as bash reads it, not by
  its prefix as a permission rule is: every command of a list, pipeline, subshell, `if` or
  substitution, its variable assignments skipped, past `command`, `exec`, `nohup` and `env`, then
  `git` or a path ending in `/git`, its global options (`-C` moves the folder judged, so
  `git -C / commit` outside the repository is not denied), and the subcommand. So
  `git -C . -c core.editor=true commit` and `make && git push` are caught, and `git log --grep
'git commit'`, where the words are an argument's text, is not. A guardrail for agents, not a
  fortress: `sh -c '…'`, `eval`, scripts, git aliases and words built from variables are not
  looked into, and the commit-msg hook, the pre-push hook and CI's `itos verify` stay the gates.
  An input it cannot read exits 1 with the reason on stderr; Claude Code blocks a tool on exit 2
  alone, which the guard never gives.

- **The guard under an itos older than it** (slice 44, `ID-GUARD-11`). The launcher hands
  `itos hook pre-tool-use` to the version a repository pins, and an itos older than 2.3.0 has no
  such hook: its usage error exits 2, which Claude Code takes as a block, so every Bash command in
  that repository would be blocked. Now, where the version the launcher chose for the hook (the
  pin, `ITOS_VERSION`, or the newest release outside a project) is older than 2.3.0, it runs and
  fetches nothing: it reads the input to its end, says why in one line on stderr, which Claude Code
  shows only in its debug output, and exits 0 with nothing on stdout, no answer:

  ```text
  itos: hook pre-tool-use answers nothing: this repository pins itos 2.2.0, and the guard needs itos 2.3.0 or later
  ```

  Every other command is handed on as before. As bug 7 did for the git shim, a repository pinned to
  an older release is unaffected by anyone's plugin.

- **`itos work list`** (slice 43, `ID-WORK-06`, `ID-WORK-07`). Every item of the work registry
  (`work.registry`, by default `work-items.yaml` in the ledger's folder), in its order, whatever
  its status, kind or owner, done ones too: its id, kind, status and title in columns, `-` for a
  kind or status it does not give. `--json` is `{"schema":1,"file","items":[…]}`, each item as
  `itos work --json` writes it. It judges nothing, as `itos task list` does not, so a registry
  with a problem still lists; no registry where itos looks is exit 1. `itos work` itself still
  proposes only what a person can start and what waits.

- **The itos plugin for Claude Code** (T-066). This repository is a plugin marketplace:
  `.claude-plugin/marketplace.json` names one plugin, `itos`, in `integrations/claude-code/`, and
  the plugin's version is itos's, so a release of itos is a release of the plugin and Claude Code
  offers the update. It calls the `itos` on your `PATH`, in every repository you open, and does
  something only where itos manages the repository:
  - **Titles.** An itos ID in Claude's replies is drawn with its title beside it, `T-066` as
    `` `T-066: The itos plugin for Claude Code` ``, and "slice 43" as the registry's `slice-43`.
    Only the drawing changes: the transcript and what Claude reads back stay as written, and IDs
    inside fenced code or a longer code span are left alone. The titles come from
    `itos work list --json` and `itos task list --json` in the session's folder, asked at the start
    of the session and of each turn and never while drawing, so a registry `work.registry` moves
    and a ledger task with no registry item are titled too. When no itos answers, or its
    `work list` gives no items (an itos older than 2.3.0 reads `work list` as `work`), they come
    from `tasks/work-items.yaml`.
  - **A skill**, `itos`, on working in such a repository: find work with `itos work` and
    `itos work list`, commit with `itos commit --task <id>` or `--scenarios <ids>`, push with
    `itos push`, read what a gate reports and fix that cause, never run the gates by hand or
    bypass a hook. A repository's own `AGENTS.md` or `CLAUDE.md` wins where it says more.
  - **The guard**: a `PreToolUse` hook on Bash runs `itos hook pre-tool-use`, above. Two shell
    guards keep it from breaking Bash where itos cannot answer: with no `itos` on the `PATH` it
    answers nothing, and an exit code 2 (an itos older than 2.3.0 on the `PATH`, which has no such
    hook) becomes 1, which Claude Code reports and lets the command run.

This repository also gained a check of its own Go dependencies (T-067: a module younger than a
week is refused, and `govulncheck` runs, whenever `go.mod` changes); it changes nothing in the
binary or for a consumer.

## Known issues

Every known issue of v2.2.0 still stands (docs/releases/v2.2.0.md, "Known issues", which keeps
v2.1.0's and v2.0.0's in turn), among them `git push` taking no arguments through the git shim
(`p3-shim-push-args`) and an extension run from a subfolder starting at the top
(`p3-extension-prefix`). New with this release:

- **The plugin runs the `itos` on the `PATH`, and only it** (`p3-plugin-project-itos`). A
  repository that installs itos for itself (`hooks.bin` naming a committed script, as the install
  script does) on a machine with no global itos gets no guard, and titles only from
  `tasks/work-items.yaml`: a registry `work.registry` moves elsewhere and ledger tasks with no
  registry item go untitled. Install a global itos of 2.3.0 or later (Upgrading, step 6); with a
  pin in the config, it runs the pinned version in that repository.

## Upgrading

Nothing here is required: v2.3.0 runs a v2.2.0 config as v2.2.0 did, and its hooks and CI as they
are. Do step 1 (the install script) or step 2 (a pin) to move to it, then steps 3 and 4; step 5
says what each commit of this release asks, which is nothing, and step 6 is the Claude Code
plugin, for whoever wants it. Commit as your project's rules ask (the install script and the pin
are `build` commits, or whatever type your rules give `itos.yaml` and `tools/bin/`).

1. **Move the install script to 2.3.0.** A project on the install script (`tools/bin/install-itos`,
   v2.0.0's Upgrading, step 1) changes its `version=` line and each platform's hash, nothing else;
   the shim `hooks.bin` names stays as it is. The script, for a project that has none yet:

   ```sh
   #!/bin/sh
   # tools/bin/install-itos: the pinned itos, into .tools/bin/
   set -eu
   version=2.3.0
   cd "$(git rev-parse --show-toplevel)"
   case "$(uname -s)-$(uname -m)" in
   Linux-x86_64) platform=linux-amd64 sum=<its line's hash> ;;
   Linux-aarch64 | Linux-arm64) platform=linux-arm64 sum=<its line's hash> ;;
   Darwin-x86_64) platform=darwin-amd64 sum=<its line's hash> ;;
   Darwin-arm64) platform=darwin-arm64 sum=<its line's hash> ;;
   MINGW*-x86_64 | MSYS*-x86_64) platform=windows-amd64 sum=<its line's hash> ;;
   *) echo "install-itos: no itos archive for $(uname -s)-$(uname -m)" >&2 && exit 1 ;;
   esac
   case "$platform" in
   windows-*) archive="itos-$version-$platform.zip" bin=.tools/bin/itos.exe ;;
   *) archive="itos-$version-$platform.tar.gz" bin=.tools/bin/itos ;;
   esac
   # What was installed, so a call with nothing to do runs nothing.
   pin=".tools/bin/itos.pin"
   if [ -x "$bin" ] && [ "$(cat "$pin" 2>/dev/null)" = "$version $sum" ]; then exit 0; fi
   tmp=$(mktemp -d)
   trap 'rm -rf "$tmp"' EXIT
   curl -fsSL -o "$tmp/$archive" "https://github.com/donvargax/itos/releases/download/v$version/$archive"
   if command -v sha256sum >/dev/null; then check="sha256sum -c -"; else check="shasum -a 256 -c -"; fi
   (cd "$tmp" && echo "$sum  $archive" | $check)
   mkdir -p .tools/bin
   case "$archive" in
   *.zip) unzip -o -q "$tmp/$archive" itos.exe -d .tools/bin ;;
   *) tar -xzf "$tmp/$archive" -C .tools/bin itos ;;
   esac
   echo "$version $sum" > "$pin"
   echo "install-itos: itos $version in $bin"
   ```

   Fill each `<its line's hash>` with that archive's hash from this release's `checksums.txt`, one
   `<hash>  <archive>` line per asset (`itos-2.3.0-linux-amd64.tar.gz`, `…-linux-arm64.tar.gz`,
   `…-darwin-amd64.tar.gz`, `…-darwin-arm64.tar.gz`, `itos-2.3.0-windows-amd64.zip`). The file
   exists only once the release is built, so these notes cannot hold it: the release's description
   prints it above them (https://github.com/donvargax/itos/releases/tag/v2.3.0), and
   `gh release download v2.3.0 -R donvargax/itos -p checksums.txt` downloads it. After publishing,
   itos's release task downloads the published linux-amd64 archive with that `checksums.txt` and
   checks one against the other, so the lines are those of the archives as published. With no
   `pin` in the config, the binary the script installs runs itself, asks for no newer release and
   fetches nothing.

2. **Or move the pin to 2.3.0.** A repository that pins a release in `itos.yaml` (v2.1.0's
   Upgrading, step 2) changes its two lines:

   ```yaml
   pin:
     version: 2.3.0
     checksums: <the SHA-256 of v2.3.0's checksums.txt>
   ```

   `pin.checksums` is the hash of the published `checksums.txt` itself, one for every platform:
   `gh release download v2.3.0 -R donvargax/itos -p checksums.txt && sha256sum checksums.txt` (or
   `shasum -a 256 checksums.txt`). Every global itos of 2.1.0 or later then runs 2.3.0 in this
   repository; a CI step that installs itos by `go install` can stay at its version, or move to
   `go install github.com/donvargax/itos/v2/cmd/itos@v2.3.0` (Go 1.27 or later; note the `/v2`).
   Each person's global itos can stay as it is, since the pin picks the version, but the plugin's
   guard and titles need a global itos of 2.3.0 or later on the `PATH` (step 6). Under a pin older
   than 2.3.0, the plugin's guard answers nothing and its titles come from `tasks/work-items.yaml`.

3. **Check `itos.yaml`'s `requires`.** 2.3.0 is past a cap such as `<2.3` or `=2.2.0`, so
   `itos version --check` would exit 1 naming the config's requires; widen it. A lower bound alone
   (`>=2.0.0`) needs no change. This release adds no key, so the config needs no higher bound; if
   your scripts, CI or instructions call `itos work list` or `itos hook pre-tool-use`, which
   earlier releases do not have, raise it to `>=2.3.0`.

4. **Point the schema line at v2.3.0's.** If `itos.yaml`'s first line names a release's
   `itos.schema.json`, make it
   `# yaml-language-server: $schema=https://github.com/donvargax/itos/releases/download/v2.3.0/itos.schema.json`.
   The schema is v2.2.0's, unchanged, so this only keeps the line on the release you run.

5. **What each commit of this release asks.** Nothing: every `feat` and `fix` since v2.2.0 says
   `Upgrading: none` (`itos commit footers Upgrading v2.2.0 v2.3.0` lists no footer to quote):

   ```text
   7d1c524 feat: deny an agent's git commit and git push in Claude Code with itos hook pre-tool-use
   b70e61a feat: list every item of the work registry with itos work list
   95d3440 feat: answer nothing for hook pre-tool-use where the launcher would run an itos without the guard
   ```

   What each changes for a project: 7d1c524 adds a hook that runs only where Claude Code is told
   to run it (step 6, or your own `.claude/settings.json`); b70e61a adds `work list` to `itos work`,
   which ran the proposal for any argument before; 95d3440 makes the launcher answer that hook
   itself under a pin older than 2.3.0, and changes nothing for any other command. The plugin
   (T-066) is published from this repository and installed by each person; nothing in a consumer's
   repository changes for it.

6. **To have Claude Code work through itos**, optional and new, per person. First put a global
   itos of 2.3.0 or later on your `PATH`: this release's archive for your platform, unpacked into
   a folder on it, or `go install github.com/donvargax/itos/v2/cmd/itos@v2.3.0` (v2.1.0's
   Upgrading, step 2, the global install). In a repository whose config has no pin,
   `itos version` then prints the version you installed. Then, in Claude Code:

   ```text
   /plugin marketplace add donvargax/itos
   /plugin install itos@itos
   ```

   Which itos answers it then:
   - in a repository that pins 2.3.0 or later, the pinned itos: titles from `itos work list`, and
     the guard;
   - in a repository that pins an older release, the launcher answers the guard with nothing, and
     the titles come from `tasks/work-items.yaml`: move the pin (step 2) for both;
   - in a repository with no pin, on the install script or not, the global itos on the `PATH`,
     while the hooks still run the script's version;
   - with no `itos` on the `PATH`, the guard answers nothing and the titles come from
     `tasks/work-items.yaml` (Known issues, `p3-plugin-project-itos`); with an `itos` older than
     2.3.0 on the `PATH`, in a repository that does not pin 2.3.0 or later, that itos has no such
     hook, so Claude Code reports the hook's error before each Bash command and runs it: install
     the global itos first;
   - in a repository itos does not manage, nothing: no guard, no titles.

   Try it in a repository itos manages: ask Claude what to work on next (it runs `itos work`, and
   the IDs in its answer carry their titles), or ask it to commit with `git commit`, which the
   guard turns into `itos commit`. The plugin's version is each itos release's
   (`/plugin marketplace update itos` fetches the newest). If you titled itos IDs with a local Claude Code mod of
   your own, remove it once the plugin is installed, or every ID is titled twice. To wire only the
   guard, without the plugin, put the hook in `.claude/settings.json`:

   ```json
   {
   	"hooks": {
   		"PreToolUse": [
   			{
   				"matcher": "Bash",
   				"hooks": [{ "type": "command", "command": "itos hook pre-tool-use" }]
   			}
   		]
   	}
   }
   ```

   The guard is per person, like the git shim: the hooks and CI stay the gates, and nothing in the
   repository changes when one person installs the plugin.

7. **Check:** `tools/bin/itos version` (or `itos version` in the repository, with a pin) prints
   `itos 2.3.0`, `tools/bin/itos config check` passes, `tools/bin/itos version --check` exits 0, and
   the commit of these changes goes through your hooks on 2.3.0.

8. **Report a problem itos causes.** To report a problem itos caused in this repository, open an
   issue on donvargax/itos with the exact command, its exact output and exit code, what
   `itos version` prints, the part of `itos.yaml` that matters, and what you expected, each under
   its own heading (What was run / Its output / itos version / The config / What was expected):

   ```sh
   gh issue create -R donvargax/itos --label consumer-report --title "consumer report: <one line>" --body-file <report.md>
   ```

   (or, in a browser, https://github.com/donvargax/itos/issues/new?template=consumer-report.yml).
   `gh issue create --template` does not fill in the form when nothing answers it, so a session
   writes the body itself, one `## ` heading per part, and passes the label. One problem per issue;
   leave out anything private, since the repository is public.
