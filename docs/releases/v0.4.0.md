# itos 0.4.0

itos runs the footer rules itself beside any header-lint delegate. `ci run` names the kind of a
merged check's run. An empty selection of named tests runs none instead of every test. A missing
ledger folder is one footer problem instead of a crash. The package installs with no install
script and declares that it needs Node 24.

No config key is added, removed or renamed, and no key's default or accepted values change.

## What is new

- **itos runs the footer rules beside the header lint, whatever the delegate.** With
  `commits.header_lint` delegating to a command, the commit-msg hook (its `hook`),
  `commit check-message` and `verify` (its `stdin`) used to run only the delegate. The footer rules
  ran only if the delegate's own config carried them, as a commitlint plugin, and a delegate
  without one skipped them without a word. itos now runs `commits.footers` itself, always, after
  the delegate: the delegate judges the header and body, itos the footers.
  - Both report before the exit, so a header problem no longer hides a footer problem. Footer
    problems print after the delegate's report, on stderr, as `✖   <message> [<rule>]`.
  - `commit check-message` exits 1 when either rejects the message. Under `--json` the
    delegate's problems and the footer rules' are one `problems` list, the delegate's first, each
    footer problem at level `error`.
  - In the hook, a failing delegate's own exit code is still the hook's. Footer problems alone
    exit 1.
  - `verify` rejects a commit whose footers break the rules, though its delegate passed it.
  - With no delegate nothing changes: the footer rules run alone, as before.

  So a commit a footer-less delegate passed can now be rejected, in the hook and in `verify` over
  a range already pushed. A delegate whose config still carries footer rules reports each footer
  problem twice, once from each. The help of `commit check-message` and `hook commit-msg` says the
  footer rules always run.

- **`ci run` names the kind of named tests a merged check ran in.** A task's check merged into the
  run of named tests was logged `= <command>   (in the E2E run above)`, whatever the kind was
  called. It is now `(in the <kind> run above)`, the kind as `tests.<kind>` names it:
  `(in the scenario run above)` for a kind called `scenario`. `--json` already named the kind and
  is unchanged.
- **An empty selection of named tests runs none, not every test.** A selection of IDs renders
  through the kind's `ids_pattern`, and with no IDs that was an empty alternation (`@(?:)\b` for a
  Gherkin kind), which matches every test.
  - With an empty smoke set, CI's merged run of named tests runs only what the push names: the
    scenarios its footers name and its task checks select.
  - With an empty smoke set and nothing named, the plan has no run of named tests at all, and
    `ci plan` lists none.
  - `itos tests smoke run <kind>` with an empty smoke set runs nothing and says so on stderr,
    `The smoke set of tests.<kind> is empty: there is nothing to run`, exit 0.

  A smoke set that lists IDs runs as before.

- **A missing footer source is one problem, not a crash.**
  - A message naming no ID reads no footer source: there is nothing to check its IDs against, and
    a missing footer is still judged.
  - A message naming a task when the ledger folder is missing, both from the tree its footer is
    read at and from the working tree, gets one problem (rule `footer-source-missing`, with a
    fix), exit 2, as for a file the config names that cannot be read. With the default ledger it
    reads:

    ```text
    FAIL itos.yaml: the Task: footer names tasks of the ledger, and its folder tasks does not exist
    ```

    Under `--json` it is the config error's object (`schema`, `config`, `valid: false`,
    `problems`). It was `itos: ENOENT: … scandir 'tasks'`, exit 2, for any message checked under a
    ledger footer, even one naming no task.

  - Since a message naming no task reads no tree, the hook and `verify` no longer print
    `<sha> has no tasks; its Task: footer is read against the working tree` for a commit before
    the ledger that names no task. It is still printed for one that names a task.
- **The package's manifest holds only what a consumer needs.** `itos-0.4.0.tgz`'s `package.json`
  is `name`, `version`, `type`, `bin`, `files` and `engines` (`"node": ">=24"`), and nothing else.
  Earlier tarballs carried this repository's `package.json` whole, so npm and pnpm listed its
  `prepare: vp config` script on every install as an install script awaiting approval. The script
  is gone, and so are the devDependencies and `packageManager`. `engines` states what the bundle
  already needed: Node 24, for `import.meta.main`. An install prints only `added 1 package`.

## Known issues

- **Only the footer rules report a missing ledger folder as a problem**
  (`p1-ledger-folder-missing`). `config check`, `task`, `task list`, `ci plan` and `ci run` still
  stop on `itos: ENOENT: … scandir 'tasks'`, exit 2, and `config check --json` then prints no JSON.
  Create the ledger folder before configuring a ledger.
- **A check merged into a run of named tests that does not happen is still logged as merged**
  (`p1-merged-check-without-a-run`). With an empty smoke set and a range that names no test, a
  task's check recognized as the smoke run (`as: smoke`) runs nothing and is logged
  `(in the <kind> run above)` under no such run.
- **Not every command pattern reads `hooks.bin` as `itos`** (`p1-itos-in-every-pattern`), as in
  v0.3.0. A `ci.covers` `matches` pattern, a `ci.nightly_only` entry and a `tests.<kind>.recognize`
  template are matched against the command as written. Keep spelling out the path there.
- **`--print-defaults` leaves out `hooks.bin`'s default** (`p1-bin-in-defaults`), `tools/bin/itos`.
- **A check two named tasks share runs once per task in CI and in the hook** (`p1-ci-checks-once`,
  `p1-hook-checks-once`). Only `itos task` runs it once.
- **`ledger.group.label` is accepted and read by nothing** (`p1-group-label-read`).
- **A `ledger.files` of `tasks/{group}.yaml` matches the registry** (`p1-ledger-matches-registry`).
  Keep the registry where `ledger.group.pattern` does not reach.
- **The commit-time data check does not follow every file the data reads**
  (`p1-people-checked-at-commit`, `p1-smoke-rule-at-commit`), and `itos verify` does not repeat it
  per commit (`p1-verify-data-per-commit`).
- **A pre-commit hook's early exit is hand-written** (`p1-pre-commit-asks-what-skips`), and
  **`shell: []` is accepted** (`p1-shell-not-empty`).

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). No config key changed, so `itos.yaml` needs no edit to keep working. What can change is
which commits pass: step 3 finds them before CI does.

1. **Use Node 24 or later** wherever itos runs: the hooks, CI and any session that calls it. The
   bundle always needed it. The manifest now says so, and npm warns (`EBADENGINE`) or, with
   `engine-strict`, refuses to install on an older Node.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v0.4.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v0.4.0/itos-0.4.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-0.4.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

   The install lists no install script for itos now. If you recorded a decision about its
   `prepare` script, drop it: an `itos` entry in npm's `allowScripts` (`npm install-scripts prune`
   removes it), or in pnpm's approved or ignored builds (what `pnpm approve-builds` wrote).

3. **The footer rules now run beside your header-lint delegate, and can reject a commit that
   passed before.** This matters if `commits.header_lint` sets `hook` or `stdin`. If your
   delegate's config carried no footer rules, `commits.footers` were not enforced until now.
   - Before your next commit, run `itos verify <from> HEAD`, with `<from>` the head of your last
     green CI run on the main branch (what `itos ci range` gives `FROM` in CI). That is the range
     your next CI run re-checks. A commit it rejects for a footer would turn that run red. If it
     is already pushed, it cannot be fixed. Set `commits.since` to the full SHA of the newest
     such commit, so verification starts after it.
   - From now on the commit-msg hook rejects a commit whose footer is missing or names an ID that
     does not exist (or is not live), as `commits.footers` says, though the delegate passed it.
     Footer problems alone exit 1. A failing delegate's own exit code is still the hook's.

4. **Drop the footer rules from your delegate's config.** If your commitlint config (or other
   delegate) carries a footer plugin, such as one `<key>-footer` rule per footer, each footer
   problem is now reported twice, once by it and once by itos. Remove the plugin and keep
   `@commitlint/config-conventional` (or your header and body rules) alone. Do it in the commit
   that changes the pin, after step 2: v0.3.0 runs no footer rules beside a delegate, so dropping
   the plugin first would leave the footers unchecked. Once it is dropped, raise `itos.yaml`'s
   `requires` to `">=0.4.0"`: an older itos would then enforce no footer rule at all.

5. **Move task checks that relied on the delegate to reject footers.** A ledger check that pipes a
   message into commitlint (`printf 'build: x\n' | vp exec commitlint`, say) and expects it to
   fail for its footer passes once the plugin is gone (step 4), so a `fails:` check turns red.
   Pipe it into `itos commit check-message -` instead. That runs `commits.header_lint.stdin` and
   then the footer rules, as the hook does, so it still rejects a bad header. Give it
   `cost: static` if the commitlint pattern made it static before.

6. **Read both reports.** Anything that parses itos's output for a message should expect the
   delegate's report and then the footer rules' lines, `✖   <message> [<rule>]`, on stderr. A
   header problem no longer hides a footer problem. Under `--json`, `commit check-message`'s
   `problems` holds the delegate's problems first, then each footer problem at level `error`, and
   `ok` is false when either rejects.

7. **A merged check's log line names its kind.** A script or agent that looks for
   `(in the E2E run above)` in `ci run`'s log must look for `(in the <kind> run above)`, the kind
   as `tests.<kind>` names it. `--json` is unchanged.

8. **An empty smoke set no longer runs every named test.** If a kind's smoke set is empty, CI used
   to run all its tests on every push by accident. Now it runs only the tests a push names, and
   none when it names none. `tests smoke run` with an empty set exits 0 having run nothing. If you
   relied on that full run, list the tests to run on every push in the smoke set, or add a
   `ci.steps` step that runs the kind whole.

9. **A missing ledger folder is a problem with a rule.** A message naming a task when the ledger
   folder is missing exits 2 with rule `footer-source-missing`, not a raw `ENOENT`. Under
   `--json` it is the config error's object (`valid: false`, `problems`), not
   `commit check-message`'s. A message naming no task no longer needs the folder. Anything
   matching the warning `<sha> has no tasks; its Task: footer is read against the working tree`
   sees it only for a commit before the ledger that names a task.

10. **Check:** `itos version` prints `itos 0.4.0`, `itos config check` passes, and a message
    missing a footer your config requires, piped into `itos commit check-message -`, is rejected
    with the footer's rule printed once.
