# itos 0.5.0

A nightly step, `{ tasks: done }`, runs the checks of every done task, so a change elsewhere cannot
break one unseen, and a failing task check's line names its task's title. A missing ledger folder is
one problem in every command that reads the ledger. A check merged into a run of named tests that
does not happen runs as itself. A `commits.since` a shallow clone lacks says the clone is shallow.

No config key is added, removed or renamed, and no key's default changes. `ci.nightly.steps`
accepts one more step shape, `{ tasks: done }` with an optional `cost: static`, which `ci.steps`
refuses.

## What is new

- **A missing ledger folder is one problem in every command that reads the ledger** (slice 14,
  the v0.4.0 known issue `p1-ledger-folder-missing`). When the folder `ledger.files` names does
  not exist, `itos config check`, `task <id>`, `task list`, `ci plan` and `ci run` print one
  problem, rule `ledger-folder-missing`, and exit 2, as before:

  ```text
  FAIL itos.yaml: the ledger's folder tasks does not exist
  ```

  They used to stop on `itos: ENOENT: … scandir 'tasks'`. `config check --json` now prints its
  report (`valid: false`, the problem with `area: ledger`) where it printed no JSON, and the other
  commands print the config error's report under `--json`. `ci run` stops before any step. The
  commit-msg hook rejects a commit that stages `itos.yaml` while the index holds no ledger folder
  with this problem, where it said "the index holds no folder tasks".

- **A check merged into a run of named tests that does not happen runs as itself** (slice 15, the
  v0.4.0 known issue `p1-merged-check-without-a-run`). With an empty smoke set and a range that
  names no test, the plan has no run of named tests, and a task check that `tests.<kind>.recognize`
  reads `as: smoke` used to be logged `(in the <kind> run above)` and never run. It now runs as
  the task wrote it: `ci run` logs `$ <command>`, and a failure fails CI; `ci plan` shows it as
  `(run)`, and `"action": "run"` under `--json`. Only `as: smoke` can select nothing, so `as: whole`
  and `as: pattern` checks are unchanged, and nothing changes when the plan has a run of named
  tests.

- **The nightly can run every done task's checks** (slice 16). A task's checks run in CI only when
  a pushed commit names the task, so a change elsewhere could break a done task's check unseen. A
  new step in `ci.nightly.steps`, `{ tasks: done }`, runs the checks of every task whose work item
  has `status: done`; a task in progress, or with no work item, is left out. With `cost: static`
  it runs only the checks the cost rule calls static. A check two done tasks share runs once, as
  in `itos task`. A red one fails the nightly, naming its task.
  - `tasks` takes only `done`, and `cost` only `static`. The step is refused in `ci.steps`
    (`config-step-tasks`): a push runs the tasks its commits name.
  - The step's checks run where it is written, a task's static checks before its late ones. A
    check another nightly step has already run is not run again, and one that is a run of a kind
    the nightly runs whole is part of that run. A `ci.nightly_only` check runs: this is the
    nightly.
  - `ci plan --nightly` lists each of the step's checks under its task, and under `--json` in
    `order`, with the tasks in `tasks`.
- **A failing task check names its task's title**, in a push's run and the nightly's:
  `CI failed at T-011 (A check that fails), its check: <command>`, where it read
  `CI failed at T-011's check: <command>`. `ci run --json`'s `failed_at` gains `title`.
- **A config problem names the wrong value of a step written as a mapping.** A step with a value
  that fits none of its shapes was reported as "should be a string, not object"; the problem now
  names the value.
- **A `commits.since` a shallow clone lacks says the clone is shallow** (slice 17). In a shallow
  clone, such as `actions/checkout`'s default one-commit checkout, `itos config check` and
  `itos verify` said `commits.since names <sha>, which is not a commit of this repository`, though
  the repository has it. They still exit 2, with the same rule (`config-since-commit`), and now
  say:

  ```text
  commits.since names <sha>, which this clone does not have: the clone is shallow, and the commit may lie beyond its history. Fetch the whole history with git fetch --unshallow, or with fetch-depth: 0 for actions/checkout
  ```

  Under `--json` the problem gains that fix. In a full clone the message is unchanged.

## Known issues

- **The nightly stops at its first failure when `ci.stop_at_first_failure` is true**
  (`p1-nightly-past-first-failure`). The setting is one for pushes and the nightly, so a red step
  hides every step after it: a red scenario in a whole run hides the done tasks' checks written
  after it. Put `{ tasks: done }` last (Upgrading, step 6). With the setting false, `ci run --json`'s
  `failed_at` still names only the first failure (`p1-ci-run-every-failure-json`); the log names
  each.
- **A range start a shallow clone lacks is not named as such** (`p1-range-start-shallow-clone`).
  Slice 17 covers `commits.since` only: `itos verify <from> HEAD`, and so `ci run` over a range
  starting at the last green run, with a `<from>` beyond a shallow clone's history ends in
  `itos: Command failed: git rev-list --no-merges --reverse <from>..HEAD`, exit 2. Fetch the whole
  history (`fetch-depth: 0`) wherever itos reads a range.
- **`ci plan --data-at <sha>` names a missing ledger folder by a scratch path**
  (`p1-data-at-ledger-folder`): `the ledger's folder /tmp/plan-data-…/tasks does not exist`, a path
  gone by the time it is read. The folder is the ledger's at `<sha>`.
- **Not every command pattern reads `hooks.bin` as `itos`** (`p1-itos-in-every-pattern`), as in
  v0.4.0. A `ci.covers` `matches` pattern, a `ci.nightly_only` entry and a `tests.<kind>.recognize`
  template are matched against the command as written. Keep spelling out the path there.
- **`--print-defaults` leaves out `hooks.bin`'s default** (`p1-bin-in-defaults`), `tools/bin/itos`.
- **A check two named tasks share runs once per task in a push's CI and in the hook**
  (`p1-ci-checks-once`, `p1-hook-checks-once`). `itos task` and the nightly's `{ tasks: done }` step
  run it once.
- **`ledger.group.label` is accepted and read by nothing** (`p1-group-label-read`).
- **A `ledger.files` of `tasks/{group}.yaml` matches the registry** (`p1-ledger-matches-registry`).
  Keep the registry where `ledger.group.pattern` does not reach.
- **The commit-time data check does not follow every file the data reads**
  (`p1-people-checked-at-commit`, `p1-smoke-rule-at-commit`), and `itos verify` does not repeat it
  per commit (`p1-verify-data-per-commit`).
- **A pre-commit hook's early exit is hand-written** (`p1-pre-commit-asks-what-skips`), and
  **`shell: []` is accepted** (`p1-shell-not-empty`).

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). No config key changed, so `itos.yaml` needs no edit to keep working; the nightly step in
step 5 is new and optional. What can change is what your next CI run does: a check it skipped may
now run (step 3), and its failure line reads differently (step 4).

1. **Use Node 24 or later** wherever itos runs, as for v0.4.0: the hooks, CI, the nightly and any
   session that calls it.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v0.5.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v0.5.0/itos-0.5.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-0.5.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

3. **A check CI skipped can now run, and fail.** This matters if a kind of named tests has an
   empty smoke set. A task check that `tests.<kind>.recognize` reads `as: smoke` was logged
   `(in the <kind> run above)` and never ran when the push named no test; it now runs as the task
   wrote it, and its failure fails CI. Before you push, run `itos task <id>` for each task with
   such a check, and fix what is red. `itos ci plan <from> HEAD` shows the check as `(run)`.

4. **Match the changed output.** Anything that reads itos's output must read:
   - `CI failed at T-… (<title>), its check: <command>` where it read
     `CI failed at T-…'s check: <command>`, in a push's `ci run` and the nightly's. `CI failed at`
     still starts it, and `ci run --json`'s `failed_at` gains `title`.
   - the problem `the ledger's folder <dir> does not exist` (rule `ledger-folder-missing`, exit 2)
     where `config check`, `task`, `task list`, `ci plan` and `ci run` printed `ENOENT`, and the
     commit-msg hook `the index holds no folder <dir>`. `config check --json` now prints its report
     there.
   - in a shallow clone, `commits.since names <sha>, which this clone does not have: …` where it
     read `…, which is not a commit of this repository`. Same rule, same exit.

5. **Drop the ledger checks that test itos rather than your project.** A `done_when` check belongs
   in your ledger when it would fail because your code or your config changed. One that would
   fail only if itos changed tests itos, and itos is proven before each release by its own
   conformance corpus and features, run against the tarball you install. Remove:
   - checks that feed itos a synthetic config or ledger (through `ITOS_CONFIG`, `--config` or
     `--ledger` on a scratch file) and expect its verdict, messages piped into
     `itos commit check-message -` or `itos hook commit-msg` under one included;
   - checks that run `itos verify` or `itos ci plan` over a recorded range of commits, and above
     all any `itos verify <sha> HEAD`: its range grows with every commit, and so does its time.
     The commit-msg hook and CI's `verify` already re-check every commit you make;
   - checks of the shape of a `--json` output.

   Keep the checks of your own config: `itos config check`; a message or a path your `itos.yaml`
   must reject, checked against it by `itos commit check-message -` or `itos commit check-paths`
   (your commit policy, your scopes); and `itos version --check`, where the release you pin is the
   proof. If itos stops doing what its notes say, report it as a bug at
   <https://github.com/donvargax/itos/issues> instead of guarding against it in your ledger. Do
   this before step 6, so the nightly does not run the checks you drop.

6. **Run your done tasks' static checks every night.** Add the step at the end of
   `ci.nightly.steps`, after your whole test run, so that with `ci.stop_at_first_failure` a red
   task check cannot stop the tests from reporting (and a red test hides the task checks: see
   Known issues):

   ```yaml
   ci:
     nightly:
       steps:
         - { tasks: done, cost: static }
   ```

   Leave out `cost: static` to run every check of the done tasks, the slow ones included. Only
   tasks whose work item is `status: done` run, so mark a finished task done in the registry.
   Raise `itos.yaml`'s `requires` to `">=0.5.0"` in the same commit, since an older itos refuses
   the step.

   The step runs the checks in your nightly's own job, so that job needs what they need in CI:
   - **the whole history.** With `actions/checkout`'s default one-commit clone, `itos config check`
     and anything else that reads history fails; with `commits.since` set it says the clone is
     shallow. Give the nightly's checkout `fetch-depth: 0`, as your CI's has.
   - **the tools and the environment** your CI job installs or sets and your nightly job does not:
     a linter such as actionlint, a browser, a token. `ci.env` is applied in both.

   Before you push the step, see what would be red, since a done task whose check broke unseen
   turns the first nightly red: run `itos task` with your done tasks' IDs (it runs their late
   checks too) in a shallow clone (`git clone --depth 1`) with only the nightly's tools, which
   also shows what the job lacks. If your nightly reports its failures from the test
   runner's output alone, gather `ci run`'s `CI failed at` lines too, or a red task check reads as
   no failing test.

7. **Check:** `itos version` prints `itos 0.5.0`, `itos config check` passes, and, with the step
   added, `itos ci plan --nightly` lists your done tasks' checks under their tasks.
