# itos 0.5.0

## What is new

- **A missing ledger folder is one problem in every command that reads the ledger** (slice 14,
  the v0.4.0 known issue `p1-ledger-folder-missing`). When the folder `ledger.files` names does
  not exist, `itos config check`, `task <id>`, `task list`, `ci plan` and `ci run` print one
  problem, rule `ledger-folder-missing`, and exit 2, as before:

  ```text
  FAIL itos.yaml: the ledger's folder tasks does not exist
  ```

  They used to stop on `itos: ENOENT: … scandir 'tasks'`. `config check --json` now prints its
  report (`valid: false`, the problem with `area: ledger`) where it printed no JSON, and the other
  commands print the config error's report under `--json`. `ci run` stops before any step. The
  commit-msg hook rejects a commit that stages `itos.yaml` while the index holds no ledger folder
  with this problem, where it said "the index holds no folder tasks".

- **A check merged into a run of named tests that does not happen runs as itself** (slice 15, the
  v0.4.0 known issue `p1-merged-check-without-a-run`). With an empty smoke set and a range that
  names no test, the plan has no run of named tests, and a task check that `tests.<kind>.recognize`
  reads `as: smoke` used to be logged `(in the <kind> run above)` and never run. It now runs as
  the task wrote it: `ci run` logs `$ <command>`, and a failure fails CI; `ci plan` shows it as
  `(run)`, and `"action": "run"` under `--json`. Only `as: smoke` can select nothing, so `as: whole`
  and `as: pattern` checks are unchanged, and nothing changes when the plan has a run of named
  tests.

- **The nightly can run every done task's checks** (slice 16). A task's checks run in CI only when
  a pushed commit names the task, so a change elsewhere could break a done task's check unseen. A
  new step in `ci.nightly.steps`, `{ tasks: done }`, runs the checks of every task whose work item
  has `status: done`; a task in progress, or with no work item, is left out. With `cost: static`
  it runs only the checks the cost rule calls static. A check two done tasks share runs once, as
  in `itos task`. A red one fails the nightly, naming its task.
  - `tasks` takes only `done`, and `cost` only `static`. The step is refused in `ci.steps`
    (`config-step-tasks`): a push runs the tasks its commits name.
  - `ci plan --nightly` lists each of the step's checks under its task, and under `--json` in
    `order`, with the tasks in `tasks`.
- **A failing task check names its task's title**, in a push's run and the nightly's:
  `CI failed at T-011 (A check that fails), its check: <command>`, where it read
  `CI failed at T-011's check: <command>`. `ci run --json`'s `failed_at` gains `title`.
- **A config problem names the wrong value of a step written as a mapping.** A step with a value
  that fits none of its shapes was reported as "should be a string, not object"; the problem now
  names the value.

## Upgrading

1. **Drop the ledger checks that test itos rather than your project.** A `done_when` check belongs
   in your ledger when it would fail because your code or your config changed. One that would
   fail only if itos changed tests itos, and itos is proven before each release by its own
   conformance corpus and features, run against the tarball you install. Remove:
   - checks that feed itos a synthetic config or ledger (through `ITOS_CONFIG`, `--config` or
     `--ledger` on a scratch file) and expect its verdict, messages piped into
     `itos commit check-message -` or `itos hook commit-msg` under one included;
   - checks that run `itos verify` or `itos ci plan` over a recorded range of commits, and above
     all any `itos verify <sha> HEAD`: its range grows with every commit, and so does its time.
     The commit-msg hook and CI's `verify` already re-check every commit you make;
   - checks of the shape of a `--json` output.

   Keep the checks of your own config: `itos config check`; a message or a path your `itos.yaml`
   must reject, checked against it by `itos commit check-message -` or `itos commit check-paths`
   (your commit policy, your scopes); and `itos version --check`, where the release you pin is the
   proof.
   If itos stops doing what its notes say, report it as a bug at
   <https://github.com/donvargax/itos/issues> instead of guarding against it in your ledger.

2. **Run your done tasks' static checks every night.** Add the step at the end of
   `ci.nightly.steps`, after your whole test run, so that with `ci.stop_at_first_failure` a red
   task check cannot stop the tests from reporting:

   ```yaml
   ci:
     nightly:
       steps:
         - { tasks: done, cost: static }
   ```

   Leave out `cost: static` to run every check of the done tasks, the slow ones included. Only
   tasks whose work item is `status: done` run, so mark a finished task done in the registry.
   Before you push it, run `itos task` on your done tasks to see what is red now: a done task
   whose check broke unseen will turn the first nightly red. Raise `itos.yaml`'s `requires` to
   `">=0.5.0"`, since an older itos refuses the step.

   The step runs the checks in your nightly's own job, so that job needs what they need in CI:
   - **the whole history.** With `actions/checkout`'s default one-commit clone, `itos config check`
     and anything else that reads history fails; with `commits.since` set it says
     `commits.since names <sha>, which is not a commit of this repository`. Give the nightly's
     checkout `fetch-depth: 0`, as your CI's has.
   - **the tools and the environment** your CI job installs or sets and your nightly job does not:
     a linter such as actionlint, a browser, a token. `ci.env` is applied in both.

   To see what would be red before you push the step, run your done tasks' static checks in a
   shallow clone (`git clone --depth 1`) with the nightly's tools.

3. **Match the new failure line.** Anything that reads `ci run`'s log for
   `CI failed at T-…'s check:` must read `CI failed at T-… (<title>), its check:` instead.
   `CI failed at` still starts it.
