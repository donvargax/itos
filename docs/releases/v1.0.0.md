# itos 1.0.0

The Go binary, released. itos is now also one file with no runtime: a static executable for linux
and darwin on amd64 and arm64 and for windows on amd64, built from `cmd/itos` with no C library
and no Node. It was ported one command group at a time, beside the TypeScript, and since the last
group landed every push's CI holds it to all 450 conformance cases and every feature, the same
judges the TypeScript answers to. Where the corpus records what itos prints and how it exits, the
two match byte for byte. The TypeScript tarball is published beside it, unchanged since v0.6.0, and
stays until phase 3 switches consumers to the binary.

For a project on the TypeScript tarball, nothing changes but the version. No config key is added,
removed or renamed, no key's default changes, and nothing that passed under v0.6.0 is rejected now:
since v0.6.0 the commits have ported itos to Go, built and published the Go release, and added
this repository's own CI and issue form, and none of them touched the TypeScript (`tools/itos/`)
or the way it is packed. The one thing to check is `itos.yaml`'s `requires`, if it caps the version
below 1 (Upgrading, step 3).

## What is new

- **The Go binary** (phase 2, T-039 to T-053). Every command the TypeScript has, the binary has:
  `config check`, `task` and `task list`, `commit check-message` and `check-paths`, `verify`,
  `tests list`, `tests smoke` and `tests moves`, `ci plan`, `ci run`, `ci scope` and `ci range`,
  `work` and `work check`, `hook commit-msg`, `hook pre-push` and `hooks install`, and `version`,
  with the same flags, the same `--help` texts, the same `--json` and the same exit codes. It
  reads the same `itos.yaml`, ledger, work registry and smoke set, and applies the same defaults
  (`itos config check --print-defaults` prints the same table). Its range providers are the
  TypeScript's: `none`, `command` and `github`. It shells out to `git` as the TypeScript does, and
  runs checks through the config's `shell` (`sh -c` by default), so a project's checks need what
  they needed before.

  The proof is the one the TypeScript has: the conformance corpus (`tools/itos/conformance/`, 450
  cases over 16 files: the command line, the config, the globs, the ledger, the messages and
  scopes, the named tests and the smoke set, verify and the moving rule, the plan, the CI driver
  and the range, the work routing and the hooks) and every feature in `features/` (83 scenarios,
  whose godog steps run whatever binary `ITOS_BIN` names in scratch repositories), run against the
  Go build on every push to `main`, and against the TypeScript as before. A change to what itos
  does now lands in both in one push, or CI is red.

  Its version is package.json's, stamped in at build, so `itos version` says `itos 1.0.0` from
  either. A Go developer can also build it: `go install github.com/donvargax/itos/cmd/itos@v1.0.0`,
  which says the same version.

- **The release holds every asset in one `checksums.txt`** (T-055). A tag now publishes:
  - `itos-1.0.0-linux-amd64.tar.gz`, `itos-1.0.0-linux-arm64.tar.gz`,
    `itos-1.0.0-darwin-amd64.tar.gz`, `itos-1.0.0-darwin-arm64.tar.gz` and
    `itos-1.0.0-windows-amd64.zip`, each holding at its top level the binary (`itos`, or
    `itos.exe`), `LICENSE` and `README.md`, and nothing else;
  - `itos.schema.json`, the config's JSON Schema (below);
  - `itos-1.0.0.tgz`, the TypeScript packed to one JavaScript file, built for Node 24, as before;
  - `checksums.txt`, the SHA-256 of every file above in `sha256sum`'s format, one line each. The
    release's description prints it too.

  Check whichever assets you downloaded beside it with
  `sha256sum --ignore-missing -c checksums.txt` (`--ignore-missing`, since it lists files you did
  not download), or, in a script, pin the asset's line:
  `echo "<its line in checksums.txt>" | sha256sum -c -` (`shasum -a 256 -c -` on macOS). A pinned line is
  what holds a release that was replaced to account; a `checksums.txt` downloaded beside the asset
  would be replaced with it. Up to v0.6.0, `checksums.txt` listed the tarball alone.

  The release job proves the very files it uploads before it publishes any: each archive lists
  exactly its three files and its binary is an executable of its platform's format and
  architecture, the linux/amd64 binary says `itos 1.0.0`, `checksums.txt` passes `sha256sum -c`,
  and the tarball installs offline with no install script and passes the corpus and every
  feature. The archives are reproducible: every entry carries the tagged commit's time, so the
  same commit built by the same Go toolchain (go.mod's `toolchain` line) gives the same bytes.

- **The config's JSON Schema, `itos.schema.json`** (T-054). An editor with a YAML language server
  (VS Code's YAML extension, or any editor using `yaml-language-server`) checks an `itos.yaml` as
  you write it, completes its keys and shows each key's description and default, once the file's
  first line names the schema:

  ```yaml
  # yaml-language-server: $schema=https://github.com/donvargax/itos/releases/download/v1.0.0/itos.schema.json
  ```

  It is JSON Schema draft 2020-12, generated from the Go config's own table of keys and defaults
  at release, never kept by hand. Like `config check`, it refuses an unknown key (a misspelling),
  a wrong type and a value not allowed. It says less than `config check`, never something
  different: what a schema cannot say (`version: 1` and the checks across keys, files and the
  ledger) is left to `itos config check`, which stays the judge. Point the line at the release
  your project pins, and change it with the pin.

- **A consumer reports a problem itos caused as an issue** (T-057), on donvargax/itos, labelled
  `consumer-report`, with the command, its output, the version, the config and what was expected
  (Upgrading, step 7).

## Known issues

Every known issue of v0.6.0 still stands (docs/releases/v0.6.0.md, "Known issues"), in both
implementations, since the binary does what the TypeScript does: `config check` accepts a
`ledger.group.label` that cannot be a flag (`p1-group-label-flag-word`) and any word in a range
check's `except_types` (`p1-moves-except-types-checked`); the commit-msg hook knows a merge by its
message (`p1-moves-merge-by-git`); `itos work check` does not name a registry left at the old
default (`p1-registry-old-default-hint`); `ledger.id` has no default (`p1-ledger-id-default`);
`wip_tag` is accepted on a command kind (`p1-wip-tag-command-kind`); the nightly stops at its first
failure (`p1-nightly-past-first-failure`, `p1-ci-run-every-failure-json`); a range start a shallow
clone lacks is not named as such (`p1-range-start-shallow-clone`); `ci plan --data-at` names a
missing ledger folder by a scratch path (`p1-data-at-ledger-folder`); a check two named tasks
share runs once per task (`p1-ci-checks-once`, `p1-hook-checks-once`); a ledger of
`<folder>/{group}.yaml` matches the registry (`p1-ledger-matches-registry`); the commit-time data
check does not follow every file (`p1-people-checked-at-commit`, `p1-smoke-rule-at-commit`,
`p1-verify-data-per-commit`); and a pre-commit hook's early exit is hand-written
(`p1-pre-commit-asks-what-skips`), and `shell: []` is accepted (`p1-shell-not-empty`).

One is the binary's alone:

- **The config's regular expressions are JavaScript's in the TypeScript and RE2 in Go**
  (`p2-config-regexp-dialect`). `ci.cost.static`, `ci.covers`' `matches`, `ledger.id` and
  `ledger.group.pattern` are compiled by each implementation's own engine, and `config check`'s
  fix for a bad one says "compiles as a JavaScript regular expression" in both. They agree on
  every pattern the corpus and this repository use, and differ on others: a lookaround (`(?=…)`,
  `(?!…)`, `(?<=…)`) or a backreference (`\1`) passes the TypeScript and fails the binary's
  `config check` (exit 2), an inline flag such as `(?i)` the reverse, and `\s` matches only ASCII
  whitespace in RE2. Before you switch, run the binary's `itos config check`: it exits 0 when your
  patterns compile in both (Upgrading, step 6).

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). `itos.yaml` needs no edit to keep working, and your next CI run does what it did under
v0.6.0. Steps 1 to 5 are the upgrade. Step 6, switching to the Go binary, is not required by this
release: it is phase 3's step, and the TypeScript tarball is published beside the binary until
then. Step 7 is how to report a problem.

1. **Use Node 24 or later** wherever the TypeScript itos runs, as for v0.6.0: the hooks, CI, the
   nightly and any session that calls it.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v1.0.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v1.0.0/itos-1.0.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-1.0.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

3. **If `itos.yaml`'s `requires` caps the version below 1, widen it.** `requires` is a list of
   comparators that must all hold, and 1.0.0 is past `<1`, `<0.7`, `<=0.6.0` or `=0.6.0`, so
   `itos version --check` would exit 1 with
   `itos 1.0.0 does not satisfy >=0.6.0 <1 (the config's requires)`. Nothing else reads it: the
   other commands run as before. A lower bound alone (`>=0.6.0`, as this repository writes it)
   needs no change, and nothing in 1.0.0 needs a higher one, since no key is new.

4. **If a script checks a download against the whole `checksums.txt`, add `--ignore-missing`.**
   `checksums.txt` now lists every asset of the release, so `sha256sum -c checksums.txt` beside
   the tarball alone fails on the files it did not download.
   `sha256sum --ignore-missing -c checksums.txt` checks the ones present (and fails if there are
   none). A pinned line, as in step 2, is unaffected.

5. **Check:** `itos version` prints `itos 1.0.0`, `itos config check` passes, and
   `itos version --check` exits 0.

6. **Switching to the Go binary is optional, and not required by this release.** Phase 3 switches
   consumers from the tarball to the binary, after the binary has shadowed the TypeScript in this
   repository's CI over many pushes; its release will say when, and how to point the hooks and CI
   at it. If you want the binary now, beside or in place of the tarball, commit an install script
   that pins the version and each platform's line from the release's `checksums.txt`, so a replaced
   release cannot pass, and installs into an ignored `.tools/bin/`:

   ```sh
   #!/bin/sh
   # tools/bin/install-itos: the pinned itos, into .tools/bin/
   set -eu
   version=1.0.0
   case "$(uname -s)-$(uname -m)" in
   Linux-x86_64) platform=linux-amd64 sum=<its line's hash> ;;
   Linux-aarch64 | Linux-arm64) platform=linux-arm64 sum=<its line's hash> ;;
   Darwin-x86_64) platform=darwin-amd64 sum=<its line's hash> ;;
   Darwin-arm64) platform=darwin-arm64 sum=<its line's hash> ;;
   MINGW*-x86_64 | MSYS*-x86_64) platform=windows-amd64 sum=<its line's hash> ;;
   *) echo "install-itos: no itos archive for $(uname -s)-$(uname -m)" >&2 && exit 1 ;;
   esac
   case "$platform" in windows-*) archive="itos-$version-$platform.zip" ;; *) archive="itos-$version-$platform.tar.gz" ;; esac
   tmp=$(mktemp -d)
   trap 'rm -rf "$tmp"' EXIT
   curl -fsSL -o "$tmp/$archive" "https://github.com/donvargax/itos/releases/download/v$version/$archive"
   if command -v sha256sum >/dev/null; then check="sha256sum -c -"; else check="shasum -a 256 -c -"; fi
   (cd "$tmp" && echo "$sum  $archive" | $check)
   mkdir -p .tools/bin
   case "$archive" in
   *.zip) unzip -o -q "$tmp/$archive" itos.exe -d .tools/bin ;;
   *) tar -xzf "$tmp/$archive" -C .tools/bin itos ;;
   esac
   .tools/bin/itos version
   ```

   Fill each `<its line's hash>` from the release's `checksums.txt` (its description prints it),
   add `.tools/` to `.gitignore`, and run the script from your package manager's install step (a
   `postinstall` or `prepare` script) and in CI. The binary reads the same `itos.yaml` and gives
   the same answers, so `.tools/bin/itos config check` should pass as the tarball's does; if it
   does not, it is the regular-expression difference (Known issues), and the fix is a pattern both
   engines compile. Switching then means pointing the shim your hooks and CI call (`hooks.bin`,
   `tools/bin/itos` by default) at `.tools/bin/itos` instead of the tarball's `itos`, and dropping
   the tarball and the Node 24 requirement once nothing else calls it. Go developers can instead
   `go install github.com/donvargax/itos/cmd/itos@v1.0.0`. Editors can use the schema line either
   way (What is new).

7. **Report a problem itos causes.** To report a problem itos caused in this repository, open an
   issue on donvargax/itos with the exact command, its exact output and exit code, what
   `itos version` prints, the part of `itos.yaml` that matters, and what you expected, each under
   its own heading (What was run / Its output / itos version / The config / What was expected):

   ```sh
   gh issue create -R donvargax/itos --label consumer-report --title "consumer report: <one line>" --body-file <report.md>
   ```

   (or, in a browser, https://github.com/donvargax/itos/issues/new?template=consumer-report.yml).
   `gh issue create --template` does not fill in the form when nothing answers it, so a session
   writes the body itself, one `## ` heading per part, and passes the label. One problem per
   issue; leave out anything private, since the repository is public.
