# itos 2.1.0

itos can be installed once per machine. The binary is now a launcher: in a repository whose
`itos.yaml` pins a release (`pin.version`, and `pin.checksums`, the SHA-256 of that release's
`checksums.txt`), it fetches that release into a cache, checks it and runs it, so one global itos
serves every repository at the version each one pins. Outside a project it keeps to the newest
release, and it says when a repository's pin has fallen behind it.

itos also takes extensions, as git does: a command it does not have runs `itos-<command>` from the
`PATH`. `itos commit` makes a commit with the footers it writes from its flags (`--task`,
`--scenarios`, one flag per footer of free text such as `--upgrading`, and `--breaking`), and
refuses up front a commit missing one its type requires. And a stealth mode lets one person hold
their own commits to itos in a repository whose team does not use it, with nothing of itos in the
tree: the config in the git folder, the links in git notes, the hooks in the git config.

v2.1.0 is additive and asks nothing of a consumer. No key is removed or renamed and no default
changes for a project's config, so a config v2.0.0 accepts, v2.1.0 accepts and reads the same, and
`hooks.bin` keeps its default, `tools/bin/itos`, until v3. A project on the install script moves to
v2.1.0 with one `build` commit, the script's version and hashes (Upgrading, step 1); the global
install and the pin are there for whoever wants them (step 2). The keys added are `pin.version` and
`pin.checksums`, and `hooks.manager` takes `git-config`.

## What is new

- **A global itos runs the version a repository pins** (slice 27, `ID-PIN-01` to `ID-PIN-08`).
  Before reading its command line, itos picks the version to run: `ITOS_VERSION` when it is set,
  else the config's `pin.version`:

  ```yaml
  pin:
    version: 2.1.0 # the release, without its v
    checksums: <the SHA-256 of that release's checksums.txt>
  ```

  When that version is not the binary called, it fetches the release from `ITOS_RELEASES`
  (`<base>/download/v<version>/<asset>`, `https://github.com/donvargax/itos/releases` by default)
  into `ITOS_CACHE` (`itos/` in the user's cache folder, `~/.cache/itos` on linux), checks
  `checksums.txt` against `pin.checksums`, then the platform's archive against its line, and runs
  that binary with the same arguments: its exit code is the run's. One hash covers every platform.
  A fetch or a check that fails exits 3 with one line naming what failed, and nothing runs in its
  place; nothing unchecked stays in the cache, and a cached release runs without fetching anything.
  `ITOS_VERSION=<x.y.z>` runs another release for one call, trusting its `checksums.txt` as
  fetched unless it is the pinned one. A config with no `pin` runs the binary that was called, so a
  repository that installs itos by script or from source keeps its binary, and a config the
  launcher cannot read is reported by that binary. The launcher reads the pin alone, so a config
  written for a newer itos still reaches the version it pins. `config check` refuses a pin without
  both keys, a `pin.version` that is not `x.y.z` and a `pin.checksums` that is not a SHA-256 in hex
  (`config-pin`, exit 2); `itos.schema.json` has the key.

- **The newest release, and its notice** (slice 28, `ID-UPDATE-01` to `ID-UPDATE-10`). Where
  there is no `itos.yaml` at all, the launcher runs the newest release it knows of: the newest of
  its own version and the stable releases its cache holds, after fetching the one the release
  server announces (`<base>/latest/download/checksums.txt`), checked against that list. It asks at
  most once a day, and only where the answer is used. In a repository pinning an older release it
  runs the pin and says so on stderr, once a day per repository:

  ```text
  itos 2.1.0 is out (this repository pins 2.0.0): https://github.com/donvargax/itos/releases/tag/v2.1.0
  ```

  It never asks in CI (the `CI` variable set) or with `ITOS_NO_UPDATE=1`, and never says in CI or
  with `ITOS_NO_UPDATE_NOTICE=1`. The question waits three seconds at most, and one with no answer
  counts as asked, so an offline machine waits once a day at most; a release server it cannot
  reach, or a newest release it cannot fetch or check, is never an error. A project's config with
  no `pin` asks nothing and runs the binary called.

- **Extensions** (slice 29, `ID-EXT-01` to `ID-EXT-08`). A command itos does not have runs the
  program `itos-<command>` found on the `PATH`, and only there, with the arguments after its name,
  unread; its exit code is the run's. A built-in always wins, and a command that is neither is still
  `unknown command: <cmd>` (exit 2). The global flags before the name apply first and reach the
  extension as `ITOS_CONFIG`, `ITOS_ROOT`, `ITOS_JSON`, `ITOS_BIN` and `ITOS_VERSION`, the last so
  that a call back runs this same version. `itos --help` lists the extensions it finds under
  "Extensions"; `itos help <command>` runs `itos-<command> --help`. An extension that cannot start
  exits 3. `docs/extensions.md` says how to write one.

- **`itos commit`** (slices 31, 36 and 37, `ID-COMMITCMD-01` to `ID-COMMITCMD-11`). It runs
  `git commit` with every argument but its own flags and writes the footers as git's `--trailer`,
  so they land whether the message comes from `-m`, `-F` or the editor, and the hooks judge them as
  they judge a typed footer. `--task` writes the footer whose source is the ledger, `--scenarios`
  the one whose source is a kind of named tests (the first of `commits.footers` each, so no flag
  depends on what a project calls them), their IDs packed onto lines of 100 characters at most.
  Each footer of free text gets a flag of its name in lower case (`--upgrading` for `Upgrading:`),
  and `--breaking <text>` writes `BREAKING-CHANGE:`, the form git reads as a trailer. Before git
  runs, a commit whose type requires a footer that neither its flags nor its message give is refused
  with exit 1, naming the flag, and nothing is committed; the type is read from `-m`, `-F <file>`,
  or HEAD's message for `--amend --no-edit`. A footer the message already has is not written again.
  `ITOS_AMEND` tells the hooks whether the commit amends. A first argument that is not a flag is
  `check-message`, `check-paths`, `footers` or a usage error, never a path, so paths go after a
  flag or after `--`: `itos commit --task T-1 -m '…' -- README.md`. Its exit code is git's.

- **The stealth mode** (slices 30, 32 to 35 and 38, `ID-STEALTH-01` to `ID-STEALTH-21`). With no
  `--config`, no `ITOS_CONFIG` and no `itos.yaml` in the root, itos reads
  `<git common dir>/itos/itos.yaml` (`.git/itos/itos.yaml` in a plain clone), which git never
  commits and every linked worktree shares. The files it names for itos's own data, the ledger, the
  registry and the smoke sets, are read beside it; a ledger footer is checked against that ledger
  at every commit, even with `read_at: commit`. Under such a config:
  - the links, the footers `--task` and `--scenarios` write, are never written into the message:
    `itos commit` hands them to the hook in `ITOS_FOOTERS` and writes them as the commit's note in
    `refs/notes/itos`, which `git push` does not send unless asked, and sets `notes.rewriteRef` so
    an amend or a rebase carries the note. The footer rules read the links from the note, and refuse
    a link typed into the message. Footers of free text and `BREAKING-CHANGE` stay in the message;
  - `itos hooks install` declares the hooks in the repository's own `.git/config`
    (`hook.itos-commit-msg`, and `hook.itos-pre-push` when `hooks.pre_push` is set), beside the
    project's own; `--manager git-config` does the same anywhere. It needs a git that runs the
    hooks its config declares, else it exits 3 saying so;
  - `itos verify` and `itos ci plan` with no range judge the commits of HEAD that no remote branch
    has, every commit when there is no remote;
  - `hooks.bin` is `itos`, the global launcher, and no people file is read, whatever the config
    says; `itos work` asks nobody who you are and proposes every item as yours (`--as <handle>`
    still shows what a handle owns, by owner);
  - with no `pin`, the newest release runs, as where there is no config at all.

  An `itos.yaml` in the root always wins: a project's config is unchanged by any of this.

- **`itos version` outside a project** (bug 4, issue #2, `ID-PIN-09`). `itos version` printed its
  version only where a config loaded, and failed with exit 2 elsewhere; it now prints it whatever
  the config. `--json` still adds `requires` and `satisfied` when a config that loads has
  `requires`, and only `--check` reads the config, failing as before (exit 2) when it cannot.

- **A missing people file no longer fails a command** (slice 35, `ID-WORK-05`, `ID-CONFIG-19`).
  In a project, a missing or malformed `work.people` file failed `work`, `work check`,
  `config check` and the commit-msg hook's check of staged data with exit 2. Now only
  `config check` mentions it, as a warning (`WARN` on stderr; under `--json` a `warnings` list,
  there only when there is one, rules `work-people-missing` and `work-people-unreadable`), and
  passes. Without people the registry's owners go unchecked and `--as` is taken as given.

- **The amend fixes.** An amend is judged as the commit it makes (bug 6, `ID-COMMITCMD-12`): the
  commit-msg hook judged the staged paths against HEAD, the commit an amend replaces, so an amend
  that only rewords a `feat` was refused for touching no path its type must change. When the commit
  amends (`ITOS_AMEND=1` from `itos commit`, or, for a commit made without it, an author matching
  HEAD's to the second), the staged data, the path rules and the moves rule read the index against
  HEAD's parent. A mistyped `itos commit` subcommand is a usage error again, never a pathspec that
  could commit one file (bug 5, `ID-COMMITCMD-05`, `ID-COMMITCMD-06`).

## Known issues

Every known issue of v2.0.0 still stands (docs/releases/v2.0.0.md, "Known issues"), among them
`config check` accepting `hook` and `stdin` beside `use: builtin` (`p3-header-lint-unread-keys`)
and a free-text footer being one line (`p3-text-footer-lines`). New with this release:

- **The launcher reads the config where itos does**, `itos.yaml` in the working folder (or
  `--config`, `ITOS_CONFIG`, `--root`) (`p3-launcher-subfolder`). A global itos run from a
  subfolder of a pinned repository finds no config, so it runs the newest release instead of the
  pin, which then fails to find the config, as itos always has there. Run it from the root, as the
  hooks and CI do.
- **The cache keeps every release it fetched** (`p3-launcher-cache-prune`), about ten megabytes
  each. Delete `ITOS_CACHE`'s version folders by hand; a later run fetches what it needs again.
- **A repository relying on a global itos has no command to set it up**
  (`p3-global-install-ci`, `p3-pin-bump`): `hooks.bin` still defaults to `tools/bin/itos`, a CI
  runner has no global itos, and moving a pin means hashing the release's `checksums.txt` by hand
  (Upgrading, step 2).
- **`itos commit --upgrading` and `--breaking` write their text as one line**
  (`p3-commit-long-text-footer`), so a text past 100 characters breaks `footer-max-line-length`;
  write a longer step as several lines in the message.
- **With no `-m` or `-F`, `itos commit` puts the footers one blank line below the editor's first
  line** (`p3-commit-editor-template`), so a subject typed there sits against them: the hook still
  reads them, but the built-in lint warns `footer-leading-blank`.
- **The stealth mode:** a stealth amend through `itos commit` replaces the note's links with its
  flags', so give `--task` again (`p3-stealth-amend-keeps-links`); `itos ci run` and
  `itos ci scope` with no range do not take the unpushed commits as `ci plan` does
  (`p3-stealth-ci-run-unpushed`); `config check` accepts `hooks.bin`, `work.people` and
  `work.identity` in a stealth config, which reads none of them (`p3-stealth-ignored-keys`); and
  `hooks install --manager git-config` does not report shims an earlier `hooks install` left in
  `.git/hooks`, which then run as well (`p3-git-config-stale-shims`).

## Upgrading

Nothing here is required: v2.1.0 runs a v2.0.0 config as v2.0.0 did, and its hooks and CI as they
are. Do step 1 to move to it, then steps 3 to 5; step 2 is the global install instead of the
script, for whoever wants it, and step 6 says what each commit of this release asks, all of which a
project on v2.0.0 already meets. Commit as your project's rules ask (the install script is a
`build` commit).

1. **Move the install script to 2.1.0.** A project on v2.0.0's install script
   (`tools/bin/install-itos`, v2.0.0's Upgrading, step 1) changes its `version=` line and each
   platform's hash, nothing else; the shim `hooks.bin` names stays as it is. The script, for a
   project that has none yet:

   ```sh
   #!/bin/sh
   # tools/bin/install-itos: the pinned itos, into .tools/bin/
   set -eu
   version=2.1.0
   cd "$(git rev-parse --show-toplevel)"
   case "$(uname -s)-$(uname -m)" in
   Linux-x86_64) platform=linux-amd64 sum=<its line's hash> ;;
   Linux-aarch64 | Linux-arm64) platform=linux-arm64 sum=<its line's hash> ;;
   Darwin-x86_64) platform=darwin-amd64 sum=<its line's hash> ;;
   Darwin-arm64) platform=darwin-arm64 sum=<its line's hash> ;;
   MINGW*-x86_64 | MSYS*-x86_64) platform=windows-amd64 sum=<its line's hash> ;;
   *) echo "install-itos: no itos archive for $(uname -s)-$(uname -m)" >&2 && exit 1 ;;
   esac
   case "$platform" in
   windows-*) archive="itos-$version-$platform.zip" bin=.tools/bin/itos.exe ;;
   *) archive="itos-$version-$platform.tar.gz" bin=.tools/bin/itos ;;
   esac
   # What was installed, so a call with nothing to do runs nothing.
   pin=".tools/bin/itos.pin"
   if [ -x "$bin" ] && [ "$(cat "$pin" 2>/dev/null)" = "$version $sum" ]; then exit 0; fi
   tmp=$(mktemp -d)
   trap 'rm -rf "$tmp"' EXIT
   curl -fsSL -o "$tmp/$archive" "https://github.com/donvargax/itos/releases/download/v$version/$archive"
   if command -v sha256sum >/dev/null; then check="sha256sum -c -"; else check="shasum -a 256 -c -"; fi
   (cd "$tmp" && echo "$sum  $archive" | $check)
   mkdir -p .tools/bin
   case "$archive" in
   *.zip) unzip -o -q "$tmp/$archive" itos.exe -d .tools/bin ;;
   *) tar -xzf "$tmp/$archive" -C .tools/bin itos ;;
   esac
   echo "$version $sum" > "$pin"
   echo "install-itos: itos $version in $bin"
   ```

   Fill each `<its line's hash>` with that archive's hash from this release's `checksums.txt`, one
   `<hash>  <archive>` line per asset (`itos-2.1.0-linux-amd64.tar.gz`, `…-linux-arm64.tar.gz`,
   `…-darwin-amd64.tar.gz`, `…-darwin-arm64.tar.gz`, `itos-2.1.0-windows-amd64.zip`). The file
   exists only once the release is built, so these notes cannot hold it: the release's description
   prints it above them (https://github.com/donvargax/itos/releases/tag/v2.1.0), and
   `gh release download v2.1.0 -R donvargax/itos -p checksums.txt` downloads it. After publishing,
   itos's release task downloads the published linux-amd64 archive with that `checksums.txt` and
   checks one against the other, so the lines are those of the archives as published. The binary
   the script installs is the launcher too, but with no `pin` in the config it runs itself, asks
   for no newer release and fetches nothing. Keep it that way: a pin beside the script would only
   have the script's binary fetch the pinned one.

2. **Or install itos once per machine and pin the repository.** Optional, and new. Install itos
   into a folder on your `PATH`, by either way:
   - `go install github.com/donvargax/itos/v2/cmd/itos@v2.1.0` (Go 1.27 or later; note the `/v2`,
     without which Go installs v1.1.0);
   - or download your platform's archive from the release, check it against its line in
     `checksums.txt` (`sha256sum --ignore-missing -c checksums.txt` beside it) and unpack its
     `itos` (or `itos.exe`) onto your `PATH`.

   Then pin the release in `itos.yaml`:

   ```yaml
   pin:
     version: 2.1.0
     checksums: <the SHA-256 of v2.1.0's checksums.txt>
   ```

   `pin.checksums` is the hash of the published `checksums.txt` itself, one for every platform,
   which you compute after the release from the file as published:
   `gh release download v2.1.0 -R donvargax/itos -p checksums.txt && sha256sum checksums.txt` (or
   `shasum -a 256 checksums.txt`). `tools/bin/itos config check` refuses a pin that is not both
   keys, `x.y.z` and a SHA-256 (`config-pin`). A later version is the same two lines. Every global
   itos of 2.1.0 or later then runs that release in this repository, whatever version it is.

   `hooks.bin` still defaults to `tools/bin/itos` through v2, so the hooks and CI still call that
   script. To drop the install script, either make the script run the global itos
   (`exec itos "$@"`) or set `hooks.bin: itos`, run `itos hooks install` again so the hooks call it,
   and change every call of `tools/bin/itos` in your config and CI to `itos`. A CI runner has no
   global itos: install one in a step of its own before itos runs, such as
   `go install github.com/donvargax/itos/v2/cmd/itos@v2.1.0` with Go set up, and the pin picks the
   version from there. Each person installs itos once; until then the hooks cannot run. If that is
   more than you want now, stay on the install script (step 1): it keeps working through v2.

3. **Check `itos.yaml`'s `requires`.** 2.1.0 is past a cap such as `<2.1` or `=2.0.0`, so
   `itos version --check` would exit 1 naming the config's requires; widen it. A lower bound alone
   (`>=2.0.0`) needs no change. If you use a key this release adds (`pin`, or
   `hooks.manager: git-config`), raise it to `>=2.1.0`: v2.0.0 refuses `pin` as an unknown key and
   `git-config` as a manager it does not know.

4. **Point the schema line at v2.1.0's.** If `itos.yaml`'s first line names a release's
   `itos.schema.json`, make it
   `# yaml-language-server: $schema=https://github.com/donvargax/itos/releases/download/v2.1.0/itos.schema.json`,
   which knows `pin` and `git-config`.

5. **Check the environment for the names itos now reads.** The launcher reads `ITOS_VERSION`
   (another release to run), `ITOS_RELEASES`, `ITOS_CACHE`, `ITOS_NO_UPDATE` and
   `ITOS_NO_UPDATE_NOTICE`; `itos commit` hands the hooks `ITOS_FOOTERS` and `ITOS_AMEND`; an
   extension is given `ITOS_CONFIG`, `ITOS_ROOT`, `ITOS_JSON`, `ITOS_BIN` and `ITOS_VERSION`. If
   your shell, hooks or CI set any of these for something else, unset it there, or itos will read
   it: an `ITOS_VERSION` left set makes every run fetch and run that release. A program on your
   `PATH` named `itos-<word>` now runs as `itos <word>`, where it was `unknown command`.

6. **What each commit of this release asks.** Every `Upgrading:` footer since v2.0.0 that says more
   than `none`, as each commit wrote it:

   ```text
   6be16c7 fix: print itos version outside a project, reading the config only for --check
   Upgrading: a script that ran itos version to find out whether a config is readable runs itos
   version --check, the one form that still reads it.

   2770228 feat: run the version a repository pins, fetched into a cache and checked
   Upgrading: none required. To run itos from one global install, pin the release in itos.yaml,
   pin: { version: <x.y.z>, checksums: <the SHA-256 of that release's checksums.txt> }, and install
   itos globally (go install, or a release archive on the PATH); the repository's install script can
   then go. Without a pin, the binary that is called runs, as before.

   39a9e06 feat: keep a global itos to the newest release, and say when a pin falls behind
   Upgrading: none required. Outside a repository with an itos.yaml, a global itos now runs the
   newest release, asked for once a day (ITOS_NO_UPDATE=1 stops the asking); a repository pinning
   an older release is told so on stderr once a day (ITOS_NO_UPDATE_NOTICE=1 hides it).

   607507a feat: run a command itos does not have as itos-<cmd> from the PATH
   Upgrading: none required. A command itos does not have now runs itos-<cmd> from the PATH where
   there is one, instead of failing as an unknown command; the main help has a paragraph on it.

   d6fd99b feat: read the config from the git folder of a repository that does not use itos
   Upgrading: none required. A repository with no itos.yaml in its root and a config at
   .git/itos/itos.yaml is now read by that config instead of running as one with no config.

   cd0d21e feat: keep a stealth commit's footers in a git note, never in its message
   Upgrading: with a stealth config, commit through itos commit: the hook refuses a typed footer

   9ead58b fix: make a bare first word of itos commit a subcommand or a usage error, never a path
   Upgrading: pass paths to itos commit after a flag or after --; a bare first word is no longer one

   f78d646 feat: declare itos's hooks in the git config, beside the project's own
   Upgrading: stealth hooks now go in .git/config; delete shims an earlier hooks install wrote

   a1be566 feat: give a stealth config one person's defaults, and stop failing on a missing people file
   Upgrading: drop hooks.bin and work.people from a stealth config, which ignores them now

   e604cb8 feat: write every footer a commit needs through itos commit, refusing a missing one up front
   Upgrading: with a stealth config, write free-text footers in the message, by itos commit --<footer>
   ```

   For a project coming from v2.0.0:
   - **6be16c7** is the one that can change what a script sees: `itos version` now exits 0 and
     prints the version wherever it runs, where it exited 2 on a config it could not read. A
     script that ran it to learn whether the config is readable runs `itos version --check`
     instead, which still reads it and fails (exit 2) when it cannot.
   - **2770228, 39a9e06, 607507a and d6fd99b** need nothing: they are the global install and the
     pin (step 2), the newest release and its notice, extensions (step 5) and the stealth config,
     none of which a project's config with no `pin` meets unless it asks.
   - **cd0d21e, 9ead58b, f78d646, a1be566 and e604cb8** are about `itos commit` and the stealth
     mode, both new in this release, so a project on v2.0.0 has nothing to change: v2.0.0 had no
     `itos commit` to pass paths to and no stealth config. They matter only to someone who ran an
     unreleased build of itos from its main branch in stealth mode, and what holds at 2.1.0 is:
     commit through `itos commit`, whose links (`--task`, `--scenarios`) go to the note and are
     refused when typed into the message, while footers of free text are written in the message,
     typed or by `--upgrading` and the like (e604cb8 narrows cd0d21e's "typed footer" to the
     links); give `itos commit` its paths after a flag or after `--`; run `itos hooks install`
     again in a stealth repository so the hooks go into `.git/config`, and delete the shims an
     earlier `hooks install` wrote into `.git/hooks`, or both run; take `hooks.bin` and
     `work.people` out of a stealth config, which ignores them.

7. **To hold yourself to itos in a repository that does not use it**, optional and new: README.md,
   "Use itos in a repository that doesn't", gives the config to put at
   `$(git rev-parse --git-common-dir)/itos/itos.yaml`, then `itos hooks install`. It needs a global
   itos (step 2), since its hooks call `itos`.

8. **Check:** `tools/bin/itos version` (or `itos version` in the repository, with a pin) prints
   `itos 2.1.0`, `tools/bin/itos config check` passes, `tools/bin/itos version --check` exits 0, and
   the commit of these changes goes through your hooks on 2.1.0.

9. **Report a problem itos causes.** To report a problem itos caused in this repository, open an
   issue on donvargax/itos with the exact command, its exact output and exit code, what
   `itos version` prints, the part of `itos.yaml` that matters, and what you expected, each under
   its own heading (What was run / Its output / itos version / The config / What was expected):

   ```sh
   gh issue create -R donvargax/itos --label consumer-report --title "consumer report: <one line>" --body-file <report.md>
   ```

   (or, in a browser, https://github.com/donvargax/itos/issues/new?template=consumer-report.yml).
   `gh issue create --template` does not fill in the form when nothing answers it, so a session
   writes the body itself, one `## ` heading per part, and passes the label. One problem per issue;
   leave out anything private, since the repository is public.
