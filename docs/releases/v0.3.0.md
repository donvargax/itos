# itos 0.3.0

The commit-msg hook runs the static checks of the tasks a commit names, every config key itos
accepts is one it reads, a cost pattern written for `itos` matches the command written as
`hooks.bin`, and one `itos task` run runs a shared check once.

## What is new

- **The commit-msg hook runs the named tasks' static checks.** For each task a `Task:` footer
  names, `itos hook commit-msg` runs that task's checks in written order up to its first late one,
  using the cost rule CI uses (a check's own `cost:`, else `ci.cost.static`'s patterns, else late).
  This rule runs last, after the header lint, so a commit another rule rejects runs no check. A
  failing check rejects the commit (exit 1, under `commits.reject_message`) when the task's work
  item is `done`, because a finished task that fails has regressed. For a task with any other
  status, or with no item, the hook prints `failing T-…` with the status, and the commit goes
  through; CI judges the push. Each check's output is printed under the task's title and command
  when it fails. An `after: push` check waits, and a task stops at its first failure. The ledger
  and the registry are read from the staged tree. The checks run in the working tree, so a check
  that reads it (`vp check`, `itos config check`) also sees what the commit leaves unstaged. Two
  new keys control the rule: `hooks.commit_msg.task_checks` (default true; false runs none) and
  `hooks.commit_msg.check_timeout` (seconds, default 60), which caps each check's own timeout. A
  check that runs past it fails, naming the key. `config check` refuses a `check_timeout` of 0 or
  less (rule `config-check-timeout`).
- **Four keys that were accepted and did nothing are now read:**
  - `work.statuses` (default `todo`, `doing`, `done`, `blocked`): `work check` accepts only the
    statuses it lists. `todo`, `doing` and `done` keep their meaning: what can start, what is
    under way, what dependencies wait on.
  - `work.groups_key` (default `phases`): the registry key under which `work check` reads each
    group's owner. Its fix for an unlisted phase names that key.
  - `tests.<kind>.smoke.every_file` (default true): false lifts the rule that every file with a
    live test has a smoke test. The listed IDs must still be live, and the success line then
    reads "Every smoke scenario is live (N in all)".
  - `hooks.manager`: `hooks install` uses the manager it names instead of the detected one, and
    `--manager` overrides both. Its value must now be one of `vp`, `git`, `husky`, `lefthook`,
    `pre-commit` or `prek`, so `config check` rejects a misspelt one.

  `config check --print-defaults` lists the new defaults.

- **Three keys of features not built yet leave the schema:** `commits.header_lint.use`,
  `commits.header_lint.alongside` and `ledger.check.pushed`. No itos release ever read them. Each
  returns with the feature that gives it a second value. Until then, a config that sets one is
  invalid. The header lint's delegate is still `commits.header_lint.hook` or `stdin`.
- **The cost rule reads a command whose first word is `hooks.bin` as `itos`.** `hooks.bin`
  defaults to `tools/bin/itos`, so a `ci.cost.static` pattern written `^itos work check` now
  matches `tools/bin/itos work check`. Each pattern is tried on the command as written and as read
  that way. A pattern that spells out the path keeps matching, and the reading can only turn a
  late command static, never the reverse. Only `hooks.bin` itself is read this way: `other/itos`
  is matched as written. The command still runs as written. CI's plan and `ci plan`, the hook's
  task checks and `config check`'s written-order problem all classify through this rule.
- **One `itos task` invocation runs each distinct check once.** Two checks are the same when they
  have the same command (whitespace collapsed) and the same timeout. The first task to list a
  check runs it. Every later task reuses that exit status and reads it by its own `run:` or
  `fails:`. A verbose run prints a reused check's command with `(ran above; its exit status
reused)`. Nothing is kept between invocations, and CI's plan and the hook still run a shared
  check once per task. One limit is accepted: a check whose answer a check above it in its own
  task would change (one that writes a file the check reads) reads the earlier run. Run that task
  alone (`itos task <id>`) when it matters.
- **`itos task list` shows each task's status in the work registry** (`todo`, `doing`, `done`,
  `blocked`, or `no item`) in a new first column, and it runs no check:

  ```text
  done     T-001  0   build    Repository scaffold
  no item  T-005  2   test     A check past its timeout
  ```

  `--json` adds `status` to each task (the item's status, or null). With no registry where itos
  looks, a note on stderr names the path, and the exit code stays 0.

## Known issues

- **The install lists an install script awaiting approval** (`p1-release-manifest`), as in
  v0.2.0. The tarball carries this repository's package.json, and npm and pnpm report its
  `prepare: vp config` script on install. Don't approve or run it: itos needs no install step, and
  the script fails without Vite+. The manifest declares no `engines`, though the bundle needs
  Node 24.
- **Not every command pattern reads `hooks.bin` as `itos`** (`p1-itos-in-every-pattern`). Only
  `ci.cost.static` reads it that way. A `ci.covers` `matches` pattern, a `ci.nightly_only` entry
  and a `tests.<kind>.recognize` template are still matched against the command as written, so one
  written for `itos` misses `tools/bin/itos`. Keep spelling out the path there.
- **`--print-defaults` leaves out `hooks.bin`'s default** (`p1-bin-in-defaults`), although it now
  decides which commands the cost rule reads as `itos`. The default is `tools/bin/itos`.
- **A check two named tasks share runs once per task in CI and in the hook** (`p1-ci-checks-once`,
  `p1-hook-checks-once`). Only `itos task` runs it once.
- **`ledger.group.label` is accepted and read by nothing** (`p1-group-label-read`). The registry's
  items keep the key `phase`, and `itos task` takes `--phase` beside `--group`, whatever the label
  says.
- **A `ledger.files` of `tasks/{group}.yaml` matches the registry** (`p1-ledger-matches-registry`),
  as in v0.2.0. With the default `ledger.group.pattern`, `tasks/work-items.yaml` is read as a
  ledger file. Keep the registry where the pattern does not reach.
- **The commit-time data check does not follow every file the data reads**
  (`p1-people-checked-at-commit`, `p1-smoke-rule-at-commit`), and `itos verify` does not repeat it
  per commit (`p1-verify-data-per-commit`), as in v0.2.0.
- **A pre-commit hook's early exit is hand-written** (`p1-pre-commit-asks-what-skips`), and
  **`shell: []` is accepted** (`p1-shell-not-empty`), as in v0.2.0.

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). Step 1 comes first because v0.3.0 refuses a config that still sets a removed key, and its
own hooks refuse with it.

1. **Delete the removed keys:** `commits.header_lint.use`, `commits.header_lint.alongside` and
   `ledger.check.pushed`. Do it before changing the pin. No release read them, so v0.2.0 accepts
   the config without them. v0.3.0 treats a config that sets one as invalid: `itos config check`
   reports `unknown key commits.header_lint.use` (or the other two) and exits 2. So does every
   other command, including `itos hook commit-msg`, which then rejects every commit. Keep
   `commits.header_lint.hook` or `stdin`, the delegate itself. If `hooks.manager` is set, it must
   be exactly one of `vp`, `git`, `husky`, `lefthook`, `pre-commit` or `prek` (lower case).
   Correct it or delete it, or the config is invalid in the same way.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v0.3.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v0.3.0/itos-0.3.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-0.3.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

   If `itos.yaml` sets `requires`, raise it to `>=0.3.0` once the config relies on anything below.

3. **The commit-msg hook can reject a commit that passed before.** A commit whose `Task:` footer
   names a `done` task is rejected when one of that task's static checks fails, or runs past
   `hooks.commit_msg.check_timeout`. Before your next commit:
   - run `itos task list` to see which tasks are `done`, then `itos task <those ids>` once. Fix
     any task that fails: from now on it rejects every commit that names it;
   - give `cost: late` to a static check that takes more than a minute, or that should not run
     at commit, or raise `hooks.commit_msg.check_timeout` (default 60 seconds);
   - expect a check that reads the working tree (`vp check`, `itos config check`) to see edits
     the commit leaves unstaged. Stage them, or stash them, or the hook may reject the commit for
     them.

   To turn the rule off, set `hooks.commit_msg.task_checks: false`. Like the data check, it runs
   only if the commit-msg shim calls `itos hook commit-msg` (as `itos hooks install` writes it).

4. **Checks that call `hooks.bin` can move from late to static.** A ledger check or `ci.steps`
   step with no `cost:` of its own whose command starts with `hooks.bin` (`tools/bin/itos` by
   default) is now static if a `ci.cost.static` pattern written for `itos` matches it. It used to
   be late. The commit-msg hook now runs it for a commit naming its task (step 3), and CI runs it
   before its late steps (the unit tests, in most configs) rather than after them. Nothing goes
   from static to late. A pattern that
   spells out the path, such as `^(tools/bin/)?itos (...)`, still matches, and you may simplify it
   to `^itos (...)`. To see what moved, compare `itos ci plan <from> <to>` over a range that names
   your tasks, before and after the pin. Give `cost: late` to any check that should stay late.
   `ci.covers`, `ci.nightly_only` and `recognize` still match the command as written (Known
   issues).

5. **Keys that were accepted and ignored are now read.** If `itos.yaml` sets one, check what it
   now does. Left out, each default behaves as v0.2.0 did:
   - `work.statuses`: `work check` and `config check` reject an item whose status is not listed
     (rule `work-unknown-status`). Keep `todo`, `doing` and `done` in the list, as itos gives
     them their meaning.
   - `work.groups_key`: each group's owner is read from that registry key, not `phases`. If your
     registry still keeps them under `phases:`, rename that key in the registry or drop the
     setting. Otherwise every item's phase "is not listed".
   - `tests.<kind>.smoke.every_file`: false lifts the rule that every file with a live test has a
     smoke test, and the success line then reads "Every smoke scenario is live".
   - `hooks.manager`: `hooks install` writes for this manager instead of the detected one. If it
     names a manager you don't use, delete it before you run `hooks install`.

6. **`itos task list` has a new first column**, the task's status from the work registry
   (`todo`, `doing`, `done`, `blocked` or `no item`). A script that parses its lines must skip that
   column. `--json` adds only the `status` key.

7. **Check:** `itos version` prints `itos 0.3.0`, and `itos config check` passes.
