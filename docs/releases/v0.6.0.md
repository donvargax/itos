# itos 0.6.0

## What is new

- **CI reads the tasks a range names from the ledger footer, whatever its key** (slice 18).
  `ci plan` and `ci run` read the tasks a pushed range names from every footer of
  `commits.footers` whose `source` is `ledger`. They used to read only a footer called `Task`, so
  a project calling its ledger footer anything else (`Work:`, say) got no task checks in CI, and
  the plan stopped on `itos.yaml has no commits.footers.Task`. With more than one ledger footer,
  the tasks of each are read; with none, a range names no task. The commit-msg hook already read
  them this way.
- **What itos prints names the ledger's folder and the prose steps as the config gives them**
  (slice 18):
  - `ci run`, for a footer naming a task the ledger lacks, says
    `No task <id> in <folder>/, though a footer names it`, the folder being the directory part of
    `ledger.files`, where it always said `tasks/`.
  - a prose-only range's first line names `ci.prose.steps`, each in backquotes:

    ```text
    Only prose changed: `vp check`, `itos config check`, and the named tasks' static and `prose: true` checks.
    ```

    where it always said `` `vp check`, and the named tasks' … ``, whatever the steps were. With
    no prose steps it reads `Only prose changed: the named tasks' static and …`.

  - the footer rule's fix for an unknown task (`--json`'s `fix`) names the ledger's folder,
    `name an id <folder>/ has, …`, where it always said `tasks/`.
  - `itos hook commit-msg --help` says the checks run for "each task a ledger footer names
    (Task: here)".

- **The defaults itos applies are the ones `config check --print-defaults` prints** (slice 19).
  They are one table, which the loader lays `itos.yaml` over (`tests.<kind>`'s under each kind),
  where each command used to write its own fallback. Where the two disagreed, the printed table
  now holds:
  - a kind that leaves out `tag_prefix` takes `@` everywhere, as `--print-defaults` always said.
    The smoke rule took no prefix there, so `itos tests smoke check` rejected a smoke set listing
    `@ID-A-01` as not a live scenario, and CI's plan selected the smoke set as `@(?:@ID-A-01)`,
    which matches nothing; both now read `ID-A-01`.
  - a Gherkin kind that leaves out `wip_tag` takes `@wip` in the footer rule's message too: a named
    test not live is reported `still tagged @wip: <id>`, where it read `not live: <id>`. A kind with
    a command adapter, which reads no wip tag, still reads `not live: <id>`.

  And `--print-defaults` (and its `--json`) now prints the defaults that were applied without being
  printed: `hooks.bin` (`tools/bin/itos`), `tests.<kind>.run.join.each` (`{p}`) and
  `tests.<kind>.run.join.sep` (`|`), and `ci.range.github.workflow` (`ci.yml`),
  `ci.range.github.branch` (`main`), `ci.range.github.repository_env` (`GITHUB_REPOSITORY`) and
  `ci.range.github.token_env` (`[GITHUB_TOKEN, GH_TOKEN]`). Their values are the ones itos already
  used.

- **Every command pattern reads `hooks.bin` as `itos`** (slice 20; it was the known issue
  `p1-itos-in-every-pattern`). A `ci.covers` rule's `matches`, a `ci.nightly_only` entry and a
  `tests.<kind>.recognize` template now read a check whose first word is `hooks.bin`
  (`tools/bin/itos` by default) as if that word were `itos`, as `ci.cost.static` has since v0.3.0.
  So `matches: "^itos work check$"`, `nightly_only: ["itos work check"]` or
  `{ command: "itos tests smoke run scenario", as: smoke }` match the check the ledger writes
  `tools/bin/itos work check` or `tools/bin/itos tests smoke run scenario`, where they matched only
  a check written `itos …`. Each is tried on the check as written and as read with `itos`, so a
  pattern that spells the path out keeps matching. A check under any other path is matched as
  written, and every check runs as written.
- **`ledger.group.label` is read** (slice 21; it was the known issue `p1-group-label-read`). It
  names what the ledger's groups are, and the tools now call a group by it where they said `phase`
  whatever it was:
  - `itos work check`'s `work-unknown-phase` and `work-unknown-phase-owner` messages and fixes say
    `<label> 7 is not listed`, `add <label> 7 to phases: in …`, `<label> 3: owner "z" is not in …`
    and `set <label> 3's owner …`. With `label: milestone`, `phase 7 is not listed` becomes
    `milestone 7 is not listed`. The rule IDs, the registry's item key `phase` and
    `work.groups_key` are unchanged.
  - `itos task` and `itos task list` take `--<label> <g>` beside `--group <g>` and `--phase <g>`,
    all three the same, so a project whose label is `milestone` may write
    `itos task --milestone 2`.
  - the usage line `itos task` prints when nothing matches names the label's flag beside `--group`:
    `itos task <id>… | --group|--<label> <g> [--skip <ids>] | --pending`.

  Its default is `phase`, now in the table `config check --print-defaults` prints, so a config
  without the key reads `phase` as before.

- **`work.registry`'s default is beside the ledger** (slice 22). Without `work.registry`, itos
  reads the work registry at `work-items.yaml` in the ledger's folder, the directory part of
  `ledger.files`, where it always read `tasks/work-items.yaml`. With the default ledger,
  `tasks/phase-{group}.yaml`, that is still `tasks/work-items.yaml`; a ledger in `work/` has its
  registry at `work/work-items.yaml`. Every command that reads the registry follows: `itos work`
  and `work check`, `itos task list`, `config check`, `ci plan` and `ci run` (the tasks still
  `todo` wait), the nightly's done tasks, and the commit-msg hook's check of staged data and its
  task checks. `no work registry at <path>` and `No work registry at <path>, …` name the new path,
  and `itos config check --print-defaults` prints `work.registry` as it applies to the config's
  ledger (`tasks/work-items.yaml` when no config loads).

- **The moving rule is itos's: a built-in range check and `itos tests moves`** (slice 23). A
  Gherkin kind's `range_checks` entry may be `{ name, builtin: moves, except_types,
allowed_renames }` in place of `staged` and `range` commands. For a commit whose type
  `except_types` does not name, live scenarios may only move between feature files: each keeps its
  ID, name, tags and steps exactly, none is lost or added, and a file with a live scenario keeps
  its header and Background; `@wip` scenarios may come, go or change, and comment lines are never
  compared. `allowed_renames` maps an ID (without its prefix) to the one new name it may take.
  The commit-msg hook judges HEAD against the index, its problems in the hook's rejection
  (`a test commit changes the live scenario ID-A-01 in features/a.feature: …`); `itos verify`
  judges each commit of its range against its parent and reports a failing one under its SHA, as
  it reports a path the type may not touch; `itos tests moves <kind>` judges HEAD against the
  index by hand (exit 1 with each problem, `--json` too). A type outside `commits.types`, when the
  config lists them, is left to the header lint, as a merge's message is. The kind's `root`,
  `id`, `tag_prefix` and `wip_tag` are its own. `itos config check` refuses `builtin` beside
  `staged` or `range`, on a kind whose adapter is not `gherkin`, and `allowed_renames` without
  `builtin`. Until now the rule was this repository's own script, which no consumer had.

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). No config key is removed or renamed, and the one place keys are added is a range check
of `tests.<kind>.range_checks`, which may now say `builtin: moves` and `allowed_renames` (step 10).
No value itos applies changes except
`tests.<kind>.tag_prefix`'s where the smoke rule and CI's smoke selection read it (step 5),
`ledger.group.label`'s, which now has the default `phase` and is read (step 8), and
`work.registry`'s, which follows the ledger's folder (step 9), so `itos.yaml` needs no edit to keep
working unless your ledger is outside `tasks/` and your registry is not beside it. What can change is what your next CI run does, if your ledger
footer is not called `Task` (step 3) or a `ci.covers`, `ci.nightly_only` or `recognize` pattern
written for `itos` meets a check that calls `hooks.bin` (step 7), and some lines of output, if your
ledger is not under `tasks/`, your prose steps are not `vp check`, a Gherkin kind leaves out
`wip_tag`, or you set `ledger.group.label` (step 4), and `itos task`'s usage line when nothing
matches, for everyone (step 4).

1. **Use Node 24 or later** wherever itos runs, as for v0.5.0.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v0.6.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v0.6.0/itos-0.6.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-0.6.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

3. **If your ledger footer is not called `Task`, CI now runs the checks of the tasks it names.**
   They did not run in CI before. Before you push, run `itos task <id>` for the tasks your commits
   since the last green run name, and fix what is red. `itos ci plan <from> HEAD` lists them.

4. **Match the changed output.** Anything that reads itos's output must read:
   - `No task <id> in <folder>/, though a footer names it`, `<folder>` being `ledger.files`'
     directory, where it read `No task <id> in tasks/, …`. Unchanged for a ledger under `tasks/`.
   - ``Only prose changed: `<step>`, …, and the named tasks' static and `prose: true` checks.``,
     naming your `ci.prose.steps`, where it read ``Only prose changed: `vp check`, and …``.
     Unchanged when your prose steps are exactly `vp check`.
   - the unknown-task fix `name an id <folder>/ has, …` under `--json`, where it read
     `name an id tasks/ has, …`.
   - `still tagged @wip: <id>` for a named test not live, where it read `not live: <id>`, when the
     footer's kind uses the Gherkin adapter and leaves out `wip_tag`. Unchanged when the kind sets
     `wip_tag`, or uses a command adapter.
   - `<label> <g> is not listed` and `<label> <g>: owner …` from `itos work check`, and
     `<label> <g>` in their fixes, where they read `phase <g>`, when `ledger.group.label` is set to
     something other than `phase`. Unchanged without the key. The rule IDs
     (`work-unknown-phase`, `work-unknown-phase-owner`) are unchanged.
   - `No matching tasks. Usage: itos task <id>… | --group|--phase <g> [--skip <ids>] | --pending`
     (with your label in place of `phase`), where it read `… | --group <g> [--skip <ids>] | …`.
     This one changes whatever the config.

5. **A kind without `tag_prefix` now reads its smoke IDs and CI's smoke selection with `@`
   stripped**, the default `--print-defaults` always printed. Nothing to do if every kind in
   `tests` sets `tag_prefix`, or uses the Gherkin adapter (whose list already read `@`). A smoke set
   the check rejected only for that reason now passes. A kind with a command adapter whose test
   IDs keep their leading `@` must set `tag_prefix: ""` to read them as before.

6. **Read the newly printed defaults.** `itos config check --print-defaults` (and `--json`) now
   lists `hooks.bin`, `tests.<kind>.run.join.each`, `tests.<kind>.run.join.sep`,
   `ci.range.github.workflow`, `ci.range.github.branch`, `ci.range.github.repository_env` and
   `ci.range.github.token_env`, with the values itos already applied. Anything that compares the
   printed defaults between versions sees them as new; no setting needs to change.

7. **Write `ci.covers`, `ci.nightly_only` and `recognize` for `itos`, if you like.** Each now reads
   a check that starts with `hooks.bin` as starting with `itos`, so you may drop the spelled-out
   path: `^(tools/bin/)?itos work check$` can be `^itos work check$`, a `nightly_only` entry
   `tools/bin/itos work check` can be `itos work check`, and a template
   `tools/bin/itos tests smoke run scenario` can be `itos tests smoke run scenario`. Nothing needs
   to change: a pattern that names the path matches as before. What can change is a pattern you
   already wrote for `itos`, which used to miss a check written with `hooks.bin` and now matches
   it, so that check no longer runs on its own in a push: it is covered, left to the nightly or
   merged into the run of named tests. If you wrote both forms (one rule or template for `itos`,
   another for the path), the first that matches now wins, as the list is read in order: a
   `recognize` template for `itos` listed above one for the path can now read the check as its
   own selection (`whole`, a pattern or the smoke set) instead, and a `ci.covers` rule above
   another names its own step as the one that covered it. `itos ci plan <from> HEAD` shows how
   each named check is read; keep one form of each, or order them so the one you mean comes
   first.

8. **`ledger.group.label` is read, with the default `phase`.** `itos config check
--print-defaults` (and `--json`) now lists `ledger.group.label: phase`, where the key had no
   default and was read by nothing. Without the key nothing changes. With it, `itos work check`
   names a group by it (step 4), and `itos task` and `itos task list` take `--<label> <g>` beside
   `--group` and `--phase`: a script may use the label's flag, and `--group` and `--phase` still
   work. Choose a label that is one word and is not another of `itos task`'s flags (`skip`,
   `pending`), since it becomes a flag.

9. **If your ledger is outside `tasks/` and you do not set `work.registry`, keep the registry
   where itos reads it.** `work.registry` now defaults to `work-items.yaml` in `ledger.files`'
   folder, so a project whose `ledger.files` is `work/phase-{group}.yaml` and whose registry is at
   `tasks/work-items.yaml` must either set `work.registry: tasks/work-items.yaml` in `itos.yaml`
   or move the registry to `work/work-items.yaml`. Until it does, `itos work check` and
   `itos config check` fail with `no work registry at work/work-items.yaml`, `itos task list`
   shows every task with `no item`, CI treats no named task as `todo`, so a task not started
   runs its checks, and the nightly's `tasks: done` step finds no done task. Nothing to do if your ledger is under `tasks/`, or `work.registry` is set.
   `itos config check --print-defaults` prints the path itos reads for your config.

10. **Adopt the moving rule, if you have a Gherkin kind and want it.** Nothing changes until you
    do. To hold every commit type but `feat` and `fix` to moving live scenarios unchanged, add the
    range check to the kind (here `scenario`):

    ```yaml
    tests:
      scenario:
        range_checks:
          - { name: scenario-moves, builtin: moves, except_types: [feat, fix] }
    ```

    Name the types that may change what a scenario checks in `except_types`. A rename you allow
    outside them goes in `allowed_renames`, by ID and new name:
    `allowed_renames: { ID-A-01: "Opens again" }`. If you ran a moves script of your own as
    `staged` and `range` commands, replace that entry with this one (a check is either built-in or
    commands, not both) and delete the script. Before you push, run `itos verify <the last green
run's head> HEAD` and `itos tests moves scenario`: a commit since then that changed a live
    scenario outside `except_types` now fails verify, and CI with it.

11. **Check:** `itos version` prints `itos 0.6.0`, and `itos config check` passes.
