# itos 0.6.0

## What is new

- **CI reads the tasks a range names from the ledger footer, whatever its key** (slice 18).
  `ci plan` and `ci run` read the tasks a pushed range names from every footer of
  `commits.footers` whose `source` is `ledger`. They used to read only a footer called `Task`, so
  a project calling its ledger footer anything else (`Work:`, say) got no task checks in CI, and
  the plan stopped on `itos.yaml has no commits.footers.Task`. With more than one ledger footer,
  the tasks of each are read; with none, a range names no task. The commit-msg hook already read
  them this way.
- **What itos prints names the ledger's folder and the prose steps as the config gives them**
  (slice 18):
  - `ci run`, for a footer naming a task the ledger lacks, says
    `No task <id> in <folder>/, though a footer names it`, the folder being the directory part of
    `ledger.files`, where it always said `tasks/`.
  - a prose-only range's first line names `ci.prose.steps`, each in backquotes:

    ```text
    Only prose changed: `vp check`, `itos config check`, and the named tasks' static and `prose: true` checks.
    ```

    where it always said `` `vp check`, and the named tasks' … ``, whatever the steps were. With
    no prose steps it reads `Only prose changed: the named tasks' static and …`.

  - the footer rule's fix for an unknown task (`--json`'s `fix`) names the ledger's folder,
    `name an id <folder>/ has, …`, where it always said `tasks/`.
  - `itos hook commit-msg --help` says the checks run for "each task a ledger footer names
    (Task: here)".

- **The defaults itos applies are the ones `config check --print-defaults` prints** (slice 19).
  They are one table, which the loader lays `itos.yaml` over (`tests.<kind>`'s under each kind),
  where each command used to write its own fallback. Where the two disagreed, the printed table
  now holds:
  - a kind that leaves out `tag_prefix` takes `@` everywhere, as `--print-defaults` always said.
    The smoke rule took no prefix there, so `itos tests smoke check` rejected a smoke set listing
    `@ID-A-01` as not a live scenario, and CI's plan selected the smoke set as `@(?:@ID-A-01)`,
    which matches nothing; both now read `ID-A-01`.
  - a Gherkin kind that leaves out `wip_tag` takes `@wip` in the footer rule's message too: a named
    test not live is reported `still tagged @wip: <id>`, where it read `not live: <id>`. A kind with
    a command adapter, which reads no wip tag, still reads `not live: <id>`.

  And `--print-defaults` (and its `--json`) now prints the defaults that were applied without being
  printed: `hooks.bin` (`tools/bin/itos`), `tests.<kind>.run.join.each` (`{p}`) and
  `tests.<kind>.run.join.sep` (`|`), and `ci.range.github.workflow` (`ci.yml`),
  `ci.range.github.branch` (`main`), `ci.range.github.repository_env` (`GITHUB_REPOSITORY`) and
  `ci.range.github.token_env` (`[GITHUB_TOKEN, GH_TOKEN]`). Their values are the ones itos already
  used.

- **Every command pattern reads `hooks.bin` as `itos`** (slice 20; it was the known issue
  `p1-itos-in-every-pattern`). A `ci.covers` rule's `matches`, a `ci.nightly_only` entry and a
  `tests.<kind>.recognize` template now read a check whose first word is `hooks.bin`
  (`tools/bin/itos` by default) as if that word were `itos`, as `ci.cost.static` has since v0.3.0.
  So `matches: "^itos work check$"`, `nightly_only: ["itos work check"]` or
  `{ command: "itos tests smoke run scenario", as: smoke }` match the check the ledger writes
  `tools/bin/itos work check` or `tools/bin/itos tests smoke run scenario`, where they matched only
  a check written `itos …`. Each is tried on the check as written and as read with `itos`, so a
  pattern that spells the path out keeps matching. A check under any other path is matched as
  written, and every check runs as written.

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). No config key is added, removed or renamed, and no value itos applies changes except
`tests.<kind>.tag_prefix`'s where the smoke rule and CI's smoke selection read it (step 5), so
`itos.yaml` needs no edit to keep working. What can change is what your next CI run does, if your
ledger footer is not called `Task` (step 3) or a `ci.covers`, `ci.nightly_only` or `recognize`
pattern written for `itos` meets a check that calls `hooks.bin` (step 7), and some lines of output,
if your ledger is not under `tasks/`, your prose steps are not `vp check` or a Gherkin kind leaves
out `wip_tag` (step 4).

1. **Use Node 24 or later** wherever itos runs, as for v0.5.0.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v0.6.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v0.6.0/itos-0.6.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-0.6.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

3. **If your ledger footer is not called `Task`, CI now runs the checks of the tasks it names.**
   They did not run in CI before. Before you push, run `itos task <id>` for the tasks your commits
   since the last green run name, and fix what is red. `itos ci plan <from> HEAD` lists them.

4. **Match the changed output.** Anything that reads itos's output must read:
   - `No task <id> in <folder>/, though a footer names it`, `<folder>` being `ledger.files`'
     directory, where it read `No task <id> in tasks/, …`. Unchanged for a ledger under `tasks/`.
   - ``Only prose changed: `<step>`, …, and the named tasks' static and `prose: true` checks.``,
     naming your `ci.prose.steps`, where it read ``Only prose changed: `vp check`, and …``.
     Unchanged when your prose steps are exactly `vp check`.
   - the unknown-task fix `name an id <folder>/ has, …` under `--json`, where it read
     `name an id tasks/ has, …`.
   - `still tagged @wip: <id>` for a named test not live, where it read `not live: <id>`, when the
     footer's kind uses the Gherkin adapter and leaves out `wip_tag`. Unchanged when the kind sets
     `wip_tag`, or uses a command adapter.

5. **A kind without `tag_prefix` now reads its smoke IDs and CI's smoke selection with `@`
   stripped**, the default `--print-defaults` always printed. Nothing to do if every kind in
   `tests` sets `tag_prefix`, or uses the Gherkin adapter (whose list already read `@`). A smoke set
   the check rejected only for that reason now passes. A kind with a command adapter whose test
   IDs keep their leading `@` must set `tag_prefix: ""` to read them as before.

6. **Read the newly printed defaults.** `itos config check --print-defaults` (and `--json`) now
   lists `hooks.bin`, `tests.<kind>.run.join.each`, `tests.<kind>.run.join.sep`,
   `ci.range.github.workflow`, `ci.range.github.branch`, `ci.range.github.repository_env` and
   `ci.range.github.token_env`, with the values itos already applied. Anything that compares the
   printed defaults between versions sees them as new; no setting needs to change.

7. **Write `ci.covers`, `ci.nightly_only` and `recognize` for `itos`, if you like.** Each now reads
   a check that starts with `hooks.bin` as starting with `itos`, so you may drop the spelled-out
   path: `^(tools/bin/)?itos work check$` can be `^itos work check$`, a `nightly_only` entry
   `tools/bin/itos work check` can be `itos work check`, and a template
   `tools/bin/itos tests smoke run scenario` can be `itos tests smoke run scenario`. Nothing needs
   to change: a pattern that names the path matches as before. What can change is a pattern you
   already wrote for `itos`, which used to miss a check written with `hooks.bin` and now matches
   it, so that check no longer runs on its own in a push: it is covered, left to the nightly or
   merged into the run of named tests. If you wrote both forms (one rule or template for `itos`,
   another for the path), the first that matches now wins, as the list is read in order: a
   `recognize` template for `itos` listed above one for the path can now read the check as its
   own selection (`whole`, a pattern or the smoke set) instead, and a `ci.covers` rule above
   another names its own step as the one that covered it. `itos ci plan <from> HEAD` shows how
   each named check is read; keep one form of each, or order them so the one you mean comes
   first.

8. **Check:** `itos version` prints `itos 0.6.0`, and `itos config check` passes.
