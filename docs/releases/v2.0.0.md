# itos 2.0.0

itos lints a commit's header itself, so a project that runs the Go binary needs no Node. Up to
v1.1.0 itos judged the header through a delegate, in practice commitlint with
`@commitlint/config-conventional`, which is Node. Now `commits.header_lint.use: builtin` lints it in
itos, by the rules config-conventional holds, each problem under commitlint's rule id and in its
words, so a project can drop commitlint and Node together.

Nothing changes for a project that keeps its delegate: `commits.header_lint.hook` and `stdin` with
no `use` run it as before, and `use: command` says so explicitly. `commits.header_lint.alongside` is
still refused.

A commit can also say what it asks of a consumer, where the change is made: a footer whose source is
free text, required for the types a project names, with a `since` of its own so that a history
written before the rule still verifies, and `itos commit footers` to gather a range's footers into a
release's notes.

The keys added are `commits.header_lint.use` and `commits.footers.<name>.since`, and
`commits.footers.<name>.source` takes `text` beside `ledger` and `{ tests: <kind> }`.

## What is new

- **The built-in header lint** (slice 25, `ID-HEADER-01` to `ID-HEADER-06`). With
  `commits.header_lint: { use: builtin }`, the commit-msg hook, `commit check-message` and `verify`
  lint the header in itos as commitlint 21 does with config-conventional. A message fails on any of
  config-conventional's errors: `type-empty`, `type-enum`, `type-case`, `subject-empty`,
  `subject-case` (not sentence-, start-, pascal- or upper-case), `subject-full-stop`,
  `header-max-length` (100), `header-trim`, `body-max-line-length` and `footer-max-line-length`
  (100, a line with a URL excepted). Its warnings, `body-leading-blank` and `footer-leading-blank`,
  are printed and never reject. `type-enum`'s list is `commits.types`, or config-conventional's own
  when the config lists none. Each problem is printed as commitlint prints one, errors before
  warnings, then itos's footer rules, which run beside it as they run beside a delegate:

  ```text
  ✖   subject may not be empty [subject-empty]
  ✖   type may not be empty [type-empty]
  ⚠   body must have leading blank line [body-leading-blank]
  ```

  Under `--json`, `commit check-message` lists each with its `level` and `fix`, the footer rules'
  after them, as it lists a delegate's. The messages commitlint leaves alone pass: a merge's, a
  revert's or a reapply's as git writes them, an `amend!`, `fixup!` or `squash!` commit, and a
  version alone. The commit-msg hook reads the message file as `commitlint --edit` does, git's
  comment lines (`core.commentChar`, `#` by default) and everything below its scissors line left
  out; `commit check-message` and `verify` read the message as given, as commitlint reads stdin.
  A blank message file passes the hook, as it passes `commitlint --edit`, and git aborts the commit
  for its empty message; a blank message on stdin is rejected, naming `type-empty` and
  `subject-empty`, where commitlint refuses it as no input. itos's own repository runs it: before
  commitlint left, the built-in lint gave commitlint's verdict on all 614 messages it was held to in
  both readings (every commit of itos's history, its test corpus's messages and messages aimed at
  each rule), and commitlint's words but for the known issue below.

- **`commits.header_lint.use` is accepted**, `builtin` or `command`. `config check` refused it as an
  unknown key from v0.3.0, since nothing read it; a value other than those two is refused now
  (`config-enum`, exit 2).

- **A footer of free text** (slice 26, `ID-UPGRADE-01` to `ID-UPGRADE-03`).
  `commits.footers.<name>.source: text` is a footer with no IDs: each line `<Key>: <text>` is one
  footer, its text whatever a consumer of the project must do, or the word `none` (alone, in lower
  case) when a consumer changes nothing. Its rule is only that it is there, for the types
  `required_for` names, and not empty, for the types `validate_for` names:

  ```yaml
  commits:
    footers:
      Upgrading: { source: text, required_for: [feat, fix, build] }
  ```

  ```text
  ✖   feat commits need a "Upgrading: <what a consumer must do, or none>" footer [upgrading-footer]
  ```

  An empty `Upgrading:` is no footer to a type that needs one, and `the Upgrading: footer is empty`
  where the type validates it. `config check` refuses `strip_prefix`, `must_be_live` and `read_at`
  on a footer of free text (`config-footer-text`, exit 2), since they say how IDs are read, and its
  problem for a source it does not know (`config-footer-source`) names `text` among the sources.

- **A footer's own since** (`ID-UPGRADE-04`). Any footer may name `since`, the full SHA of a
  commit, as `commits.since` does: `verify` leaves that commit and its ancestors out of the footer's
  `required_for`, so adding a required footer to a project's rules does not fail every commit
  written before it. The commit-msg hook and `commit check-message` judge the commit being made and
  always require it. `config check` and `verify` check it as they check `commits.since`: a full SHA
  (`config-since`), a commit the repository has (`config-since-commit`, exit 2), the shallow clone
  named as the likely cause.

- **`itos commit footers <name> <from> <to>`** (`ID-UPGRADE-05`) lists the range's footers of a
  free-text footer, one line each, oldest commit first, the commit's short SHA and the text, leaving
  out those that say `none` and empty ones; a commit with several gives a line for each. `--json`
  gives `{"schema":1,"footer","range","footers":[{"sha","subject","text"}]}`, each with the full
  SHA. The range is `from..to` as git reads it, every commit up to `<to>` when `from` is empty or
  all zeros, and is not narrowed by `commits.since`. It exits 2 for a footer that is not free text.

## Known issues

- **`subject-case` may name more cases than commitlint for a subject with some accented letters.**
  commitlint finds start-case and pascal-case after decomposing every precomposed letter (NFD); Go's
  standard library has no such tables, and the built-in lint decomposes only the letters of Latin-1
  and Latin Extended-A. For a subject such as `Ǎb Cd` it says `subject must not be sentence-case,
start-case` where commitlint says `subject must not be sentence-case`. The verdict is the same:
  every case `subject-case` refuses is sentence-case too.

## Upgrading

Do these in order, in one session, then commit as your project's rules ask.

1. **To drop commitlint and Node, switch to the built-in header lint.** In `itos.yaml`, replace
   `commits.header_lint`'s `hook` and `stdin` with `use: builtin`:

   ```yaml
   commits:
     header_lint: { use: builtin }
   ```

   Then take commitlint out: its config (`commitlint.config.*`, or the `commitlint` key of
   `package.json`), `@commitlint/cli` and `@commitlint/config-conventional`, and Node itself if
   nothing else needs it. Check it: `printf 'update things\n' | itos commit check-message -` exits 1
   naming `[type-empty]`, and a sound message of yours exits 0.

   The built-in lint holds config-conventional's rules and nothing else. If your commitlint config
   changes them (a rule of its own, a plugin, another level or limit, its own `type-enum`), keep the
   delegate with `use: command` instead, or accept config-conventional's rules. The built-in lint's
   type list is `commits.types`, so make it the list your commitlint config allowed. A script that
   reads the lint's report finds the same lines, `✖   <words> [<rule>]`, but on stderr where the
   delegate's went to stdout, without commitlint's `⧗   --- input ---` heading and its `found N
problems` summary; under `--json` nothing changes.

2. **To keep your delegate, do nothing.** `hook` and `stdin` with no `use` run it as before. Write
   `use: command` beside them if you want the choice said.

3. **To have each commit say what it asks of a consumer, add a footer of free text.** Optional, and
   new: name it, the types that need it, and `since`, the full SHA of the commit you add it after
   (`git rev-parse HEAD`), so that `verify` does not require it of the commits written before:

   ```yaml
   commits:
     footers:
       Upgrading: { source: text, required_for: [feat, fix], since: "<full SHA>" }
   ```

   Then `itos commit footers Upgrading <last release> HEAD` lists what your next release's notes
   must tell your consumers.
