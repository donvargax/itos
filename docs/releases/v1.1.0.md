# itos 1.1.0

The config's regular expressions are RE2 in both implementations. v1.0.0 shipped the Go binary
beside the TypeScript tarball with one difference between them: the TypeScript compiled the
config's patterns as JavaScript's regular expressions and the binary as RE2, Go's, so a lookaround
or a backreference passed the TypeScript's `config check` and failed the binary's. RE2 is now the
dialect of both, since the binary is what remains after phase 3's switch and RE2 matches in linear
time, so no pattern in a project's config can hang a commit hook.

For a project on the TypeScript tarball, one thing can change: a config whose patterns use what RE2
cannot compile, such as a lookaround or a backreference, is now refused by `config check` (exit 2),
as v1.0.0's binary already refused it (Upgrading, step 4). For a project on the binary, a kind's
`tests.<kind>.id` is now checked too. In both, the refusal's words name RE2. No config key is added,
removed or renamed, no key's default changes, and nothing else since v1.0.0 changed what itos
accepts, prints or packs.

## What is new

- **The config's patterns are RE2** (slice 24 and `p2-pattern-re2-escapes`, `ID-PATTERN-01` to
  `ID-PATTERN-03`). The five keys compiled as regular expressions, `ledger.id`,
  `ledger.group.pattern`, `tests.<kind>.id`, `ci.cost.static` and `ci.covers`' `matches`, are RE2 in
  the TypeScript and the binary alike, and `config check` refuses one RE2 cannot compile, in both,
  with exit 2, the rule `config-regexp` and the same words:

  ```text
  FAIL itos.yaml: ledger.group.pattern is not an RE2 regular expression: (?=\d)\d+
  ```

  and, under `--json`, the fix
  `correct ledger.group.pattern so that it compiles as an RE2 regular expression (no lookaround or backreference)`.
  Up to v1.0.0 the message said "is not a regular expression" and the fix "compiles as a
  JavaScript regular expression", in both implementations.

  The TypeScript cannot run RE2, so it still compiles each pattern with JavaScript's `RegExp`,
  which it runs the pattern with, and refuses beside that every pattern RE2 cannot compile, by
  parsing it as Go's `regexp/syntax` does: a lookaround, a backreference, a letter escape RE2 has
  no reading for, a class RE2 cannot close or name, and a repeat count above 1000 (Upgrading, step
  4, lists them). A pattern RE2 compiles and JavaScript cannot, such as `(?i)abc`, is still refused
  by the TypeScript, which could not run it, and accepted by the binary.

- **`tests.<kind>.id` is checked** (found in T-042). `config check` did not compile a kind's ID
  pattern in either implementation, so a bad one failed only when a command used it. It is now
  checked as the other four keys are, after `ci.covers`, and named as `tests.<kind>.id`.

## Known issues

Every known issue of v1.0.0 still stands but the one this release fixes (docs/releases/v1.0.0.md,
"Known issues"), in both implementations.

- **The TypeScript matches a pattern by JavaScript's rules.** On a pattern both dialects compile,
  matching is RE2's from this release, and the TypeScript's differs where JavaScript's does: `\s`
  matches Unicode whitespace in JavaScript and only ASCII whitespace in RE2, and `.` matches `\r`
  in RE2 but not in JavaScript. The gap closes when phase 3 switches consumers to the binary.
  Every pattern in the corpus and in this repository matches the same in both.

- **The TypeScript does not model RE2's caps on a compiled pattern's size and nesting depth**,
  which only patterns thousands of characters long reach: such a pattern can pass the TypeScript's
  `config check` and be refused by the binary's. A differential run against Go's `regexp` over
  635,992 patterns found no other disagreement.

## Upgrading

Do these in order, in one session, then commit as your project's rules ask (the pin is a `build`
commit). A project still on v0.6.0 does steps 6 and 7 too; one on v1.0.0 can skip them unless its
`requires` names 1.0.

1. **Use Node 24 or later** wherever the TypeScript itos runs, as for v1.0.0.

2. **Change the pin.** Check the tarball against its SHA-256, then point `package.json`'s `itos`
   dependency at the v1.1.0 URL (the lockfile records its integrity):

   ```sh
   url=https://github.com/donvargax/itos/releases/download/v1.1.0/itos-1.1.0.tgz
   curl -fsSLO "$url"
   echo "{sha256}  itos-1.1.0.tgz" | sha256sum -c -
   npm install --save-dev "$url"   # or: pnpm add -D "$url"
   ```

   If `itos.yaml`'s first line names v1.0.0's `itos.schema.json`, point it at v1.1.0's. The schema
   is unchanged, so this only keeps the line with the pin.

3. **If you run the Go binary, change its pin too.** In the install script v1.0.0's Upgrading,
   step 6, gave (https://github.com/donvargax/itos/releases/tag/v1.0.0), set the version and each
   platform's hash from this release's `checksums.txt`, printed above these notes, then run it:

   ```sh
   version=1.1.0
   # and in each platform's case, sum=<that archive's hash in v1.1.0's checksums.txt>
   ```

   `.tools/bin/itos version` then prints `itos 1.1.0`. Go developers instead run
   `go install github.com/donvargax/itos/cmd/itos@v1.1.0`. The binary already refused every
   pattern step 4 lists, but for a kind's `id`, which it now checks too.

4. **If `config check` now refuses a pattern, rewrite it as RE2.** A config whose `ledger.id`,
   `ledger.group.pattern`, `tests.<kind>.id`, `ci.cost.static` or `ci.covers`' `matches` uses what
   RE2 cannot compile is now refused by `config check` (exit 2) in the TypeScript, as v1.0.0's Go
   binary already did, and every command that loads the config stops on it. The TypeScript refuses a
   lookaround (`(?=…)`, `(?!…)`, `(?<=…)`, `(?<!…)`), a backreference (`\1`, `\k<name>`), a letter
   escape RE2 has no reading for (`\c`, `\e`, `\u`, and any letter but `\A` `\b` `\B` `\d` `\D` `\p`
   `\P` `\Q` `\s` `\S` `\w` `\W` `\x` `\z` `\a` `\f` `\n` `\r` `\t` `\v`, or inside a class `\b`,
   `\A`, `\B`, `\Q` and `\z` too), the classes `[]` and `[^]` (RE2 reads a `]` right after `[` or
   `[^` as a member), a Unicode or POSIX class name RE2 lacks (`\p{Foo}`, `[[:foo:]]`), a range
   bounded by a class (`[a-\d]`), `(?i-:…)`, and a repeat count above 1000 (`a{1001}`, `\d{1,1001}`,
   or nested counted repeats past 1000 copies, as `(a{100}){11}`). Rewrite the pattern without them:
   a lookahead that only guards what follows is usually the same pattern with that part matched
   (`^vp check(?= )` as `^vp check `), a backreference spelled out for the cases it meets, `\e` as
   the `e` JavaScript read it as, `[\b]` as `\x08`, and a long count split (`\d{1,1001}` as
   `\d{1,1000}\d?`). A kind's `id` is checked for the first time, so a pattern there that does not
   compile at all is refused too.

5. **If a script reads `config check`'s words for a bad pattern, update it.** The message now
   reads `<key> is not an RE2 regular expression: <pattern>` and the fix
   `correct <key> so that it compiles as an RE2 regular expression (no lookaround or backreference)`,
   in the TypeScript and the binary alike; the rule, `config-regexp`, is unchanged, and is the
   thing to match on.

6. **If `itos.yaml`'s `requires` caps the version below 1.1.0, widen it.** `requires` is a list of
   comparators that must all hold, and 1.1.0 is past `<1`, `<1.1` or `=1.0.0`, so
   `itos version --check` would exit 1 with
   `itos 1.1.0 does not satisfy >=1.0.0 <1.1 (the config's requires)`. Nothing else reads it: the
   other commands run as before. A lower bound alone (`>=0.6.0`, as this repository writes it)
   needs no change, and nothing in 1.1.0 needs a higher one, since no key is new.

7. **If a script checks a download against the whole `checksums.txt`, add `--ignore-missing`.**
   Since v1.0.0 `checksums.txt` lists every asset of the release, so `sha256sum -c checksums.txt`
   beside the tarball alone fails on the files it did not download.
   `sha256sum --ignore-missing -c checksums.txt` checks the ones present (and fails if there are
   none). A pinned line, as in step 2, is unaffected.

8. **Check:** `itos version` prints `itos 1.1.0`, `itos config check` passes, and
   `itos version --check` exits 0. Switching to the Go binary stays optional, as v1.0.0's
   Upgrading, step 6, says; its install script takes `version=1.1.0` and this release's
   `checksums.txt`, as in step 3.

9. **Report a problem itos causes.** To report a problem itos caused in this repository, open an
   issue on donvargax/itos with the exact command, its exact output and exit code, what
   `itos version` prints, the part of `itos.yaml` that matters, and what you expected, each under
   its own heading (What was run / Its output / itos version / The config / What was expected):

   ```sh
   gh issue create -R donvargax/itos --label consumer-report --title "consumer report: <one line>" --body-file <report.md>
   ```

   (or, in a browser, https://github.com/donvargax/itos/issues/new?template=consumer-report.yml).
   `gh issue create --template` does not fill in the form when nothing answers it, so a session
   writes the body itself, one `## ` heading per part, and passes the label. One problem per
   issue; leave out anything private, since the repository is public.
