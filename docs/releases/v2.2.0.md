# itos 2.2.0

git goes through itos. `itos push` is the routine that ends a piece of work: it pulls the branch's
upstream with a rebase, then pushes HEAD in a separate step, and never forces. itos now finds a
repository's `itos.yaml` from any subfolder of it, and the launcher runs the pin from there. And a
git shim, opt-in and per machine, makes every `git commit` and `git push` in a repository itos
manages run as `itos commit` and `itos push`, whoever types them (a person, a script, an editor or
an agent), while every other git command runs the real git untouched.

v2.2.0 is additive and asks nothing of a consumer. No key is added, removed or renamed and no
default changes, so a config v2.1.0 accepts, v2.2.0 accepts and reads the same, and `hooks.bin`
keeps its default, `tools/bin/itos`, until v3. A project on the install script moves to v2.2.0
with one `build` commit, the script's version and hashes (Upgrading, step 1); a project that pins
a release moves with the pin's two lines (step 2). The git shim is for whoever wants it, on their
own machine (step 7). Every commit of the release says `Upgrading: none` (step 6).

## What is new

- **`itos push`** (slice 39, `ID-PUSH-01` to `ID-PUSH-04`). The routine that ends a piece of work,
  after its commits, as one command. It fetches the branch's upstream (`branch.<name>.remote` and
  `branch.<name>.merge`, else `origin` and the branch's own name), rebases the branch onto it with
  `--no-autostash`, so `pull.rebase` and `rebase.autostash` change nothing, checks that no rebase
  is in progress and no conflict is left, then pushes HEAD to the upstream's branch in a separate
  step, the pre-push hook running as for any push. It refuses to start (exit 1) while tracked files
  have uncommitted changes (untracked ones are no reason), while a rebase is in progress or a
  conflict is left, and on a detached HEAD. A rebase that stops is left in progress, nothing is
  pushed, and it says how to go on: resolve, `git rebase --continue`, then `itos push` again, or
  `git rebase --abort`. Only HEAD goes, to that one branch, whatever the config's push refspecs
  say, so the stealth mode's `refs/notes/itos` stays local; under a stealth config it sets
  `notes.rewriteRef` first, as `itos commit` does, so the rebase carries the notes. It never
  forces: `--force`, `-f`, `--force-with-lease` or a `+` refspec is a usage error (exit 2), as is
  any other argument, and a push the remote or the hook refuses is reported with git's exit code,
  not retried. Nothing to push is success, and a branch the remote does not have yet is pushed
  without a rebase. `-q` leaves out the success line; `--json` gives
  `{"schema":1,"ok","outcome","remote"?,"branch"?,"commit"?}`. It reads no config, so it runs
  where itos is not set up, as `itos commit` does.

- **The config found from a subfolder** (slice 40, `ID-CONFIG-20`, `ID-PIN-10`). itos read
  `itos.yaml` only from the folder it ran in, so a run from a subfolder found no config (exit 2),
  and a global itos there ran the newest release instead of the pin. Now, with no `--config`, no
  `ITOS_CONFIG`, no `--root` and no `itos.yaml` in the folder, a run inside a git repository asks
  git for its top level and, finding `itos.yaml` (or the stealth config) there, runs as if started
  at the top, as `--root <top>` would: every path the config names means what it means at the top,
  and the launcher runs the version pinned there. A folder's own `itos.yaml` still wins, a run at
  the top asks git nothing more, and outside a repository nothing changes.

  **A path you type** is read from the folder you stand in, as git reads one, and named from the
  top: `itos commit check-paths`'s paths, `commit check-message`'s file, `work check`'s file,
  `hook commit-msg`'s file, `config check --ledger` and `tests smoke check --features`. So
  `itos commit check-paths --type docs guide.md` run in `docs/` judges `docs/guide.md`. `itos commit`
  runs git in that folder, so its pathspecs and its `-F` file mean what they meant. Under `--root` a
  typed path is still read from the root. `tests list --at` takes a tree, not a path, and is
  unchanged. An extension started from a subfolder runs at the top, with `ITOS_ROOT` naming it, as
  under `--root` (see Known issues, `p3-extension-prefix`).

- **The git shim** (slice 41 and bug 7, `ID-SHIM-01` to `ID-SHIM-08`). itos acts as git when it
  is started under the name `git`, through a link named `git` (`git.exe` on windows) to the itos
  binary, in a folder before the real git on the `PATH`. One binary, so the shim is the itos
  version in effect, launcher and pin included.
  - **Turning it on and off.** `itos git-shim install` links the itos binary that was called as
    `git` beside it, or in `--dir <folder>`, and says whether that folder comes before the real git
    on the `PATH`; put it first if not, and run `hash -r` in a shell that has already looked git
    up. `itos git-shim uninstall [--dir <folder>]` removes the link. Neither replaces nor removes a
    `git` that is not a link to itos (exit 1); `install` replaces a link to another itos. Both run
    the binary called, never a version a pin names, so a pin never links a cached release.
  - **What it intercepts, and where.** In a repository itos manages (an `itos.yaml` in the folder
    git runs in or at the repository's top, or a stealth config), from any folder of it,
    `git commit …` runs as `itos commit …` and `git push …` as `itos push …`, with git's arguments,
    none read as an itos global flag. So a commit missing a footer its type requires is refused
    before git runs, `git commit --task T-001 -m '…'` writes the footer, and `git push --force` is
    refused. git's `-C <path>` and `-c <name>=<value>` before the command are honoured (editors
    commit with `git -c <key>=<value> commit`), and `--no-pager` and `-P` change nothing. Any other
    option there (`--git-dir`, `--work-tree`, …), or `GIT_DIR` or `GIT_WORK_TREE` set, names a
    repository the shim does not follow, and runs the real git. Every other command, and every
    command in a repository itos does not manage, runs the real git (the first `git` on the `PATH`
    that is not itos) with its arguments, input, terminal and exit code untouched, at the cost of
    starting itos and a few file checks; with no such git the shim exits 3. `git commit --help`
    is git's.
  - **itos's own git.** itos never runs the `git` on the `PATH` any more: every git it starts is
    the real one, and it sets `ITOS_GIT` to it for everything it starts, so a git that a hook, a
    check or an older pinned itos runs under an itos run passes straight through the shim, and
    `itos commit` cannot run itself again.
  - **Under a pin older than 2.2.0** (bug 7). In a pinned repository `git commit` and `git push`
    are the pinned itos's. A release older than 2.2.0 has no shim to hand them to, so where the
    pin, or `ITOS_VERSION`, names one, `git commit` and `git push` run the real git with their
    arguments, after one line on stderr:

    ```text
    itos: git commit runs the real git: this repository pins itos 2.1.0, and the git shim needs itos 2.2.0 or later
    ```

  - **The gates stay the gates.** The shim is per machine and opt-in; the commit-msg hook, the
    pre-push hook and CI's `itos verify` judge every commit whoever made it, shim or not. With the
    shim on, a hand-typed `git commit --amend` goes through `itos commit`, which tells the hook it
    amends, rather than leaving the hook to guess from the author's date.

## Known issues

Every known issue of v2.1.0 still stands (docs/releases/v2.1.0.md, "Known issues", which keeps
v2.0.0's in turn), but one: this release closes `p3-launcher-subfolder`, a global itos run from a
subfolder of a pinned repository running the newest release instead of the pin. New with this
release:

- **Through the shim, `git push` takes no arguments** (`p3-shim-push-args`). In a repository itos
  manages, `git push` is `itos push`, which takes none, so `git push -u origin <branch>`,
  `git push origin HEAD`, `git push --tags` and `git push --help` are usage errors there (exit 2),
  and a tool that pushes a named branch fails. Push the current branch with `git push` alone, or
  run the real git for the rest (`ITOS_GIT=<path to git> git push …` passes through the shim, as
  does `git --git-dir=.git push …`), or turn the shim off.
- **An extension run from a subfolder starts at the top** (`p3-extension-prefix`). Since a run
  from a subfolder moves to the repository's top before an extension runs, a relative path you
  typed after the extension's name, which itos never reads, no longer means what it meant, and
  nothing tells the extension the folder you stood in. Give an extension paths from the top, or
  absolute ones, or run it from the top.

## Upgrading

Nothing here is required: v2.2.0 runs a v2.1.0 config as v2.1.0 did, and its hooks and CI as they
are. Do step 1 (the install script) or step 2 (a pin) to move to it, then steps 3 to 5; step 6
says what each commit of this release asks, which is nothing, and step 7 is the git shim, for
whoever wants it. Commit as your project's rules ask (the install script and the pin are `build`
commits, or whatever type your rules give `itos.yaml` and `tools/bin/`).

1. **Move the install script to 2.2.0.** A project on the install script (`tools/bin/install-itos`,
   v2.0.0's Upgrading, step 1) changes its `version=` line and each platform's hash, nothing else;
   the shim `hooks.bin` names stays as it is. The script, for a project that has none yet:

   ```sh
   #!/bin/sh
   # tools/bin/install-itos: the pinned itos, into .tools/bin/
   set -eu
   version=2.2.0
   cd "$(git rev-parse --show-toplevel)"
   case "$(uname -s)-$(uname -m)" in
   Linux-x86_64) platform=linux-amd64 sum=<its line's hash> ;;
   Linux-aarch64 | Linux-arm64) platform=linux-arm64 sum=<its line's hash> ;;
   Darwin-x86_64) platform=darwin-amd64 sum=<its line's hash> ;;
   Darwin-arm64) platform=darwin-arm64 sum=<its line's hash> ;;
   MINGW*-x86_64 | MSYS*-x86_64) platform=windows-amd64 sum=<its line's hash> ;;
   *) echo "install-itos: no itos archive for $(uname -s)-$(uname -m)" >&2 && exit 1 ;;
   esac
   case "$platform" in
   windows-*) archive="itos-$version-$platform.zip" bin=.tools/bin/itos.exe ;;
   *) archive="itos-$version-$platform.tar.gz" bin=.tools/bin/itos ;;
   esac
   # What was installed, so a call with nothing to do runs nothing.
   pin=".tools/bin/itos.pin"
   if [ -x "$bin" ] && [ "$(cat "$pin" 2>/dev/null)" = "$version $sum" ]; then exit 0; fi
   tmp=$(mktemp -d)
   trap 'rm -rf "$tmp"' EXIT
   curl -fsSL -o "$tmp/$archive" "https://github.com/donvargax/itos/releases/download/v$version/$archive"
   if command -v sha256sum >/dev/null; then check="sha256sum -c -"; else check="shasum -a 256 -c -"; fi
   (cd "$tmp" && echo "$sum  $archive" | $check)
   mkdir -p .tools/bin
   case "$archive" in
   *.zip) unzip -o -q "$tmp/$archive" itos.exe -d .tools/bin ;;
   *) tar -xzf "$tmp/$archive" -C .tools/bin itos ;;
   esac
   echo "$version $sum" > "$pin"
   echo "install-itos: itos $version in $bin"
   ```

   Fill each `<its line's hash>` with that archive's hash from this release's `checksums.txt`, one
   `<hash>  <archive>` line per asset (`itos-2.2.0-linux-amd64.tar.gz`, `…-linux-arm64.tar.gz`,
   `…-darwin-amd64.tar.gz`, `…-darwin-arm64.tar.gz`, `itos-2.2.0-windows-amd64.zip`). The file
   exists only once the release is built, so these notes cannot hold it: the release's description
   prints it above them (https://github.com/donvargax/itos/releases/tag/v2.2.0), and
   `gh release download v2.2.0 -R donvargax/itos -p checksums.txt` downloads it. After publishing,
   itos's release task downloads the published linux-amd64 archive with that `checksums.txt` and
   checks one against the other, so the lines are those of the archives as published. With no
   `pin` in the config, the binary the script installs runs itself, asks for no newer release and
   fetches nothing.

2. **Or move the pin to 2.2.0.** A repository that pins a release in `itos.yaml` (v2.1.0's
   Upgrading, step 2) changes its two lines:

   ```yaml
   pin:
     version: 2.2.0
     checksums: <the SHA-256 of v2.2.0's checksums.txt>
   ```

   `pin.checksums` is the hash of the published `checksums.txt` itself, one for every platform:
   `gh release download v2.2.0 -R donvargax/itos -p checksums.txt && sha256sum checksums.txt` (or
   `shasum -a 256 checksums.txt`). Every global itos of 2.1.0 or later then runs 2.2.0 in this
   repository; a CI step that installs itos by `go install` can stay at its version, or move to
   `go install github.com/donvargax/itos/v2/cmd/itos@v2.2.0` (Go 1.27 or later; note the `/v2`).
   Each person's global itos can stay as it is, since the pin picks the version, but the git shim
   (step 7) is in the binary linked, so whoever wants it installs a global itos of 2.2.0 or later.

3. **Check `itos.yaml`'s `requires`.** 2.2.0 is past a cap such as `<2.2` or `=2.1.0`, so
   `itos version --check` would exit 1 naming the config's requires; widen it. A lower bound alone
   (`>=2.0.0`) needs no change. This release adds no key, so the config needs no higher bound; if
   your scripts, CI or instructions call `itos push`, which earlier releases do not have, raise it
   to `>=2.2.0`.

4. **Point the schema line at v2.2.0's.** If `itos.yaml`'s first line names a release's
   `itos.schema.json`, make it
   `# yaml-language-server: $schema=https://github.com/donvargax/itos/releases/download/v2.2.0/itos.schema.json`.
   The schema is v2.1.0's, unchanged, so this only keeps the line on the release you run.

5. **Check what itos now reads and runs.**
   - **`ITOS_GIT`**: itos now reads it as the git to run, and sets it for everything it starts. If
     your shell, hooks or CI set it for something else, unset it there, or every git itos runs is
     that program.
   - **`push` and `git-shim` are now built-in commands**, and a built-in always wins: a program on
     your `PATH` named `itos-push` or `itos-git-shim` no longer runs as `itos push` or
     `itos git-shim`. Rename it, or call it by its own name.
   - **From a subfolder**, itos now reads the repository top's `itos.yaml` where it failed with
     exit 2 for want of a config. A script that ran itos from a subfolder on purpose to get that
     failure, or that passed `--root "$(git rev-parse --show-toplevel)"`, can drop it; a script
     that gave a typed path (a `check-paths` path, a message file) relative to the top while
     standing in a subfolder gives it relative to where it stands, or runs from the top, or passes
     `--root`, under which typed paths are read from the root as before.

6. **What each commit of this release asks.** Nothing: every `feat` and `fix` since v2.1.0 says
   `Upgrading: none` (`itos commit footers Upgrading v2.1.0 v2.2.0` lists no footer to quote):

   ```text
   b639adb feat: add itos push, the pull-rebase-push routine as one command
   dab08f0 feat: find itos.yaml at the repository top from a subfolder
   69bdee1 feat: run git commit and git push as itos's through a git shim
   4629840 fix: run the real git for commit and push under a pin older than the git shim
   ```

   What each changes for a project, all of it covered above: b639adb adds a command (step 5 for an
   `itos-push` extension); dab08f0 makes a run from a subfolder read the top's config (step 5);
   69bdee1 adds `itos git-shim` and makes itos run the real git and set `ITOS_GIT` (step 5), and
   nothing else changes until someone installs the shim (step 7); 4629840 keeps the shim from
   failing under a pin older than 2.2.0, so a repository pinned to 2.1.0 or 2.0.0 is unaffected by
   anyone's shim but for one line on stderr.

7. **To have `git commit` and `git push` go through itos**, optional and new, per person and per
   machine. With a global itos of 2.2.0 or later on your `PATH`:

   ```sh
   itos git-shim install                                # a link named git beside the itos binary
   itos git-shim install --dir ~/.local/bin/itos-shim   # or in a folder of your choice
   ```

   It says whether that folder comes before the real git on the `PATH`; if not, put it first
   (`export PATH="$HOME/.local/bin/itos-shim:$PATH"` in your shell's profile), and run `hash -r` in
   a shell that has already looked git up. To turn it off: `itos git-shim uninstall`, or
   `itos git-shim uninstall --dir <the folder>`. Which itos a `git commit` runs then:
   - in a repository that pins 2.2.0 or later, the pinned itos's `commit` and `push`;
   - in a repository that pins an older release, the real git, after one line on stderr (bug 7):
     move the pin (step 2) for the shim to act there;
   - in a repository on the install script, with no pin, the global itos that is linked, since a
     config with no pin runs the binary called, while the hooks still run the script's version.
     A global itos of 2.2.0 reads every config that 2.0.0 to 2.2.0 accept, so its `itos commit`
     judges your commits by your config, and the hook judges them again;
   - in a repository itos does not manage, the real git.

   Through the shim `git push` takes no arguments (Known issues, `p3-shim-push-args`). The hooks
   and CI stay the gates: nothing in the repository changes when one person turns the shim on.

8. **Check:** `tools/bin/itos version` (or `itos version` in the repository, with a pin) prints
   `itos 2.2.0`, `tools/bin/itos config check` passes, `tools/bin/itos version --check` exits 0, and
   the commit of these changes goes through your hooks on 2.2.0.

9. **Report a problem itos causes.** To report a problem itos caused in this repository, open an
   issue on donvargax/itos with the exact command, its exact output and exit code, what
   `itos version` prints, the part of `itos.yaml` that matters, and what you expected, each under
   its own heading (What was run / Its output / itos version / The config / What was expected):

   ```sh
   gh issue create -R donvargax/itos --label consumer-report --title "consumer report: <one line>" --body-file <report.md>
   ```

   (or, in a browser, https://github.com/donvargax/itos/issues/new?template=consumer-report.yml).
   `gh issue create --template` does not fill in the form when nothing answers it, so a session
   writes the body itself, one `## ` heading per part, and passes the label. One problem per issue;
   leave out anything private, since the repository is public.
